    Image Signature Verification¶

    A Pipeline can require every version's images to be signed, and a config version's commit to be signed, before the version is promoted anywhere. kardinal checks the signatures in the registry with sigstore-go: a key (cosign sign --key) or a Sigstore keyless identity (cosign sign from CI with OIDC). A version that does not pass is never promoted.

    apiVersion: kardinal.io/v1alpha1
kind: Pipeline
metadata:
  name: my-app
  namespace: my-app
spec:
  git:
    url: https://github.com/myorg/gitops-repo
  imageVerification:
    images: ["ghcr.io/myorg/*"]          # which Bundle images; empty = all
    authorities:
      - name: release-key
        key:
          secretRef: {name: cosign-pub, key: cosign.pub}
      - name: ci
        keyless:
          issuer: https://token.actions.githubusercontent.com
          subject: https://github.com/myorg/my-app/.github/workflows/release.yml@refs/heads/main
    commits:
      requireSigned: true                # config Bundles: the commit must be signed
    timeout: 10m
  environments:
    - name: staging
    - name: prod

    kubectl create secret generic cosign-pub -n my-app --from-file=cosign.pub
kubectl label secret cosign-pub -n my-app kardinal.io/referenceable=true
kardinal create bundle my-app --image ghcr.io/myorg/my-app@sha256:4c3b...   # by digest

    Every Secret a policy names (key, trusted root, registry credentials) must carry the label kardinal.io/referenceable: "true", as for every Secret a kardinal resource names: the Secret's owner opts in. Without it the controller does not read the Secret, and the verification waits with status.reason: SecretNotReferenceable until the label is added or the timeout passes.

    Fields¶

    spec.imageVerification:

    Field Default Description
    images[] all Repository patterns of the version images to verify; * matches any characters. Patterns and version images are compared in normalized form: the registry host lowercased and without :443, docker.io for Docker Hub (index.docker.io, registry-1.docker.io or no host) and library/ for official images (nginx is docker.io/library/nginx). A version image that does not parse as a reference fails the version.
    authorities[] Accepted signers, up to 10. An image is verified when one of its signatures verifies against any one authority. Each has a name and exactly one of key and keyless.
    authorities[].key.secretRef {name, key}: a Secret in the Pipeline namespace with the PEM public key (cosign.pub).
    authorities[].key.requireTransparencyLog false Require a Rekor entry, checked against the Sigstore public-good log. Without it a key signature is checked against the key alone (cosign verify --insecure-ignore-tlog).
    authorities[].keyless.issuer OIDC issuer of the signing certificate.
    authorities[].keyless.subject / subjectRegExp The certificate's subject (exactly one of the two). subjectRegExp must match the whole subject: it is anchored as ^(?:...)$.
    authorities[].keyless.trustedRootRef public good {name, key}: a Secret with a Sigstore trusted_root.json, for a private Sigstore. Without it the controller fetches the public-good trusted root through TUF (from tuf-repo-cdn.sigstore.dev) on first use and again once a day; a failed refresh keeps the previous root and is retried after 5 minutes. Each TUF request times out after 20s; a request answered 5xx or 429, or that fails in transport, is tried up to 3 times, a 404 ends it at once, and a whole fetch of the root takes at most 2 minutes.
    commits.requireSigned false A config or mixed version's configRef.commitSHA must be signed with a signature the SCM verified (GitHub, GitLab, Forgejo and Gitea report it; Bitbucket and Azure DevOps do not, and such a version fails). See Signed commits.
    commits.allowedSigners[] any person Also require the signer to be one of these SCM logins or emails. Platform signatures (web-flow, gitlab-system, forgejo-instance) are accepted only when listed.
    commits.authorities[] Names of keyless authorities: kardinal verifies the commit's gitsign (Sigstore) signature itself against them, instead of asking the SCM. GPG and SSH signatures are then refused, and allowedSigners does not apply. GitHub, Forgejo and Gitea only. See Commit signatures with gitsign.
    signatureRepository next to the image Where the signatures are, when they are not next to the images (cosign's COSIGN_REPOSITORY).
    registrySecretRef.name anonymous A kubernetes.io/dockerconfigjson Secret in the Pipeline namespace for private registries.
    insecureRegistries[] Registry hosts read over plain HTTP. Every other registry is HTTPS only.
    timeout 10m How long a missing signature is waited for (CI may sign after it pushes).
    attestations[] In-toto attestations each image must or may carry, up to 10: see Attestations.

    Signature formats¶

    • Sigstore bundles attached as OCI referrers: cosign v3's default, and cosign v2 with --new-bundle-format. Key and keyless. The bundle must be a cosign image signature: a DSSE in-toto statement with predicate type https://sigstore.dev/cosign/sign/v1 whose subject is the image digest. Attestations (SBOM, provenance) and plain message signatures attached to the same image are not signatures of it, whoever signed them. Up to 32 signature bundles and 64 bundles of the attestations the policy names are read per image, each against its own limit. A referrer whose dev.sigstore.bundle.predicateType annotation names a predicate the policy does not verify is skipped before it counts, and so are kardinal's own promotion receipts (annotation kardinal.io/receipt). Other attestations on the image therefore cannot crowd out its signatures or the attestations the policy reads. The referrers index itself, and every manifest, is read up to 4 MiB (tens of thousands of referrers); a larger one fails the read, and the image is not verified.
    • Legacy cosign signatures in the sha256-<digest>.sig tag (cosign v2's default): key authorities only. A keyless signature must be a Sigstore bundle.

    With requireTransparencyLog, the Rekor entry is checked offline from the bundle: its signed entry timestamp and inclusion proof against the Rekor public key in the trusted root. The controller does not query Rekor, so an entry that the log no longer serves is not noticed.

    How it runs¶

    1. Digests are required. Verifying a tag and then promoting the tag would let a different image be pushed under the tag in between. When the policy selects an image that the version names by tag, the version fails before any environment, with condition InvalidSpec (reason GraphBuildFailed): image ... is not pinned by digest. A Subscription creates versions by digest; from CI, pass --image repo@sha256:....
    2. The Bundle's Graph creates one ImageVerification (kubectl get imageverifications) with the selected images and the policy. Its controller reads the signatures from the registry and the commit's signature from the SCM, and records a result per image in status.images.
    3. The first environments (those with no upstream) wait in Pending with the message waiting for image verification <name>: ..., and so do their pre-deploy hooks. Nothing is committed or deployed.
    4. Verified: the environments start. Later environments need nothing more: their upstream already waited. Failed: the waiting steps fail, and the version with them. A signature that does not verify against an authority (another signer's, an attestation, one that is malformed) is not a verdict: an image can carry other signatures before CI's arrives, so the verification keeps waiting for one that verifies, and fails at the timeout (status.reason: SignatureNotVerified, with every reason in the message). It fails at once when a cosign signature made with a policy key names another digest, or when the commit is not signed as required. A registry or SCM outage is retried, never treated as verified, until the timeout. Each registry fetch times out after 45s and each check after 2 minutes; up to 4 ImageVerifications are checked at once.
    5. Before it promotes, the step compares the version's images with the images the ImageVerification verified (both normalized) and refuses to promote when a digest differs or a verified image is missing. The version's images cannot change anyway: the Bundle CRD refuses an update of spec.images.

    status.reason is one of SecretNotReferenceable, SecretNotFound, InvalidPublicKey, InvalidTrustedRoot, InvalidRegistryCredentials, SignatureNotVerified, CommitNotVerified, AttestationNotVerified, SLSALevelTooLow and Timeout. A key, trusted root or .dockerconfigjson that does not parse is reported by Secret and key name only; nothing of its content is copied to the status.

    Policy changes. An ImageVerification's spec is immutable, and its name carries a hash of it. Editing spec.imageVerification gives each version a new ImageVerification; the first environments that have not started yet wait for the new verdict. Environments that already started are not checked again.

    update.strategy: argocd writes an image pinned by digest as <tag>@<digest> (see Argo CD native promotion), so the digest that was verified is the one deployed. The kustomize and Helm strategies write the digest too.

    Attestations¶

    New in v0.13.0 (unreleased)

    v0.12.0 and earlier verify signatures and signed commits only. The changelog lists every change since v0.12.0.

    A signature says who signed an image. Attestations say how it was built and what is in it: SLSA provenance, a vulnerability scan with VEX statements, test results, or any other in-toto predicate. With attestations, the ImageVerification also reads each image's attestations from its OCI referrers, verifies them against the policy's authorities, and records what they say in status.attestations. Gates then decide in CEL, per environment, over attestations.*.

    spec:
  imageVerification:
    authorities:
      - name: release
        keyless: {issuer: https://token.actions.githubusercontent.com,
                  subjectRegExp: '^https://github\.com/myorg/[^/]+/\.github/workflows/release\.yml@refs/tags/.*$'}
      - name: security
        key: {secretRef: {name: security-pub, key: cosign.pub}}
    attestations:
      - name: provenance                # gates read attestations.provenance
        predicateType: https://slsa.dev/provenance/v1
        authorities: [release]          # who may sign it
        required: true                  # missing at the timeout: Failed
        slsa:
          builders:                     # runDetails.builder.id -> the level you grant it
            - id: https://github.com/slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@refs/tags/v2.1.0
              level: 3
          minLevel: 2                   # below it at the timeout: Failed
      - name: vulns
        predicateType: https://cosign.sigstore.dev/attestation/vuln/v1
        authorities: [release]
        required: true
        vex:
          authorities: [security]       # who may say a finding does not apply
      - name: tests
        predicateType: https://in-toto.io/attestation/test-result/v0.1
        authorities: [release]
---
apiVersion: kardinal.io/v1alpha1
kind: PolicyGate
metadata:
  name: prod-supply-chain
  namespace: my-app
  labels: {kardinal.io/applies-to: prod}
spec:
  expression: >-
    attestations.provenance.slsa.buildLevel >= 3 &&
    attestations.provenance.slsa.sourceCommit == bundle.provenance.commitSHA &&
    attestations.vulns.effective.critical == 0
  message: prod needs level-3 provenance from the version's commit and no critical vulnerability

    Attach them with cosign, as Sigstore bundles in the image's referrers (cosign v3, or v2 with --new-bundle-format):

    cosign attest --new-bundle-format --type slsaprovenance1 --predicate provenance.json "$IMAGE"
cosign attest --new-bundle-format --type vuln --predicate trivy.json "$IMAGE"
cosign attest --new-bundle-format --key security.key --type openvex --predicate vex.json "$IMAGE"

    attestations[]:

    Field Default Description
    name Lower-case letters and digits; the gate reads attestations.<name>.
    predicateType The in-toto predicate type, exactly.
    authorities[] Names of authorities that may sign it. An attestation from any other signer is not used.
    required false Hold the version until every image carries a verified attestation of the type; at the timeout it fails (status.reason: AttestationNotVerified). Without it the attestation is recorded when it is there, and holds nothing.
    slsa.builders[] {id, level}: the SLSA build level (1 to 3) you grant a provenance builder (runDetails.builder.id, exactly). Provenance from a builder not listed is level 1.
    slsa.minLevel 0 Hold the version while an image's level is below it; at the timeout it fails (SLSALevelTooLow).
    vex.authorities[] Names of authorities whose OpenVEX attestations count against the scan's findings. The scan's own signer does not suppress its findings unless it is listed.
    vex.predicateType https://openvex.dev/ns The predicate type of the VEX attestations.
    maxAge How old the attestation may be, a Go duration (24h): see Attestation age.
    datedBy logTime: date a key-signed attestation whose statement gives no time by its log or timestamp time. Anyone can log an old signature again or stamp it anew, so such an attestation can be made to look fresh: see Attestation age.

    What is checked. An attestation counts when its bundle verifies against one of its authorities (key, keyless, private trusted root, as for signatures), its in-toto statement's subject is the image's digest, and its predicate type is the policy's. An attestation's time is the earliest of its verified timestamps (transparency log or timestamp authority): a later log entry or timestamp over the same signature only shows that it existed then. Of several, the newest by that time (else the last referrer) is used, and count says how many verified; with a maxAge, the one that stays fresh longest is used (see Attestation age). A bundle that does not verify is never used; its reason is in message.

    SLSA build level. A build level is a property of the builder, not a field of the provenance: the policy grants it in slsa.builders. A SLSA verification summary (VSA, predicate type https://slsa.dev/verification_summary/v1) signed by one of the attestation's authorities, with verificationResult: PASSED and a resourceUri that names the image's digest, raises the level to the highest SLSA_BUILD_LEVEL_n it lists. slsa.levelSource says which decided (builder or vsa). The provenance's source, the first resolvedDependencies entry with a gitCommit digest, is recorded as sourceCommit and sourceURI.

    Vulnerabilities and VEX. The scan formats read are cosign's vuln predicate (https://cosign.sigstore.dev/attestation/vuln/v1, what cosign attest --type vuln writes) holding a Trivy or Grype report, and in-toto vulns v0.2 (https://in-toto.io/attestation/vulns). A finding is effective unless the latest OpenVEX statement for its ID (or an alias), and a product that names the image (<repository>@<digest>, the digest, or its pkg:oci purl), says not_affected or fixed; affected and under_investigation keep it. The status counts the findings by severity (critical, high, medium, low, unknown) before and after VEX, and lists the IDs of the effective critical and high ones (at most 50). To bound how old a scan may be, set its maxAge (Attestation age).

    Several images. A version with several images gets one value per attestation name in gates: verified when every image is, the lowest build level, the summed counts and the oldest scan. The signer, digest, predicate, builder, source and scanner are set there only when every image has the same one. Otherwise an expression that reads them fails, and the gate blocks. attestations.<name>.images holds each image's own result, for checks one image at a time (attestations.*).

    Bounds. Each attestation's predicate is kept as canonical JSON (sorted keys) of at most 64 KiB, and a status holds at most 256 KiB of them; the largest are dropped first. A dropped predicate keeps its summary, and predicateOmitted says why: an expression that reads it then fails, so the gate blocks rather than passes. The predicate is the build's own text: a gate may compare it, as data.

    Timing. Verified is terminal, as for signatures: an attestation added later, or a vulnerability found later, is not seen by that version, except through maxAge below. An attestation not required that is missing when the rest verified is recorded as not verified.

    Attestation age¶

    A version can wait at a gate for days; without a bound, prod promotes it on the scan it was verified with, however old. maxAge bounds it:

    attestations:
  - name: vulns
    predicateType: https://cosign.sigstore.dev/attestation/vuln/v1
    authorities: [release]
    maxAge: 24h

    # prod: a scan no older than its maxAge, with no critical finding after VEX
expression: '!attestations.vulns.stale && attestations.vulns.effective.critical == 0'
    • Age. An attestation's age counts from the time its signed statement gives (statementTime, timeSource: statement): a scan's scannedAt, a SLSA provenance's runDetails.metadata.finishedOn (v0.2: metadata.buildFinishedOn; with both present, the earlier), a SLSA verification summary's timeVerified. When it also has a verified signing time (the earliest transparency log or timestamp authority time), the earlier of the two counts, so a statement cannot claim to be newer than its signature; and never later than when kardinal first saw it (datedAt).
    • A keyless attestation whose statement gives no time counts from its verified signing time (timeSource: certificate) when its certificate lives at most an hour. Every verified time must fall inside the certificate's validity, a Fulcio certificate's ten minutes from signing, so a fresh log entry or timestamp over an old keyless signature does not verify. One whose certificate lives longer (a private CA's) is dated like a key signature.
    • A key-signed one whose statement gives no time cannot be dated: anyone can log an old signature again, or get a new timestamp over it, and push it back with only that new observation. It is stale at once unless the policy sets datedBy: logTime, which dates it by its log or timestamp time (timeSource: log). Use that only when you accept that risk.
    • An attestation with a time more than 5 minutes ahead of the controller's clock (a scanner with a wrong clock, or a date that was made up) cannot be dated either.

    One that cannot be dated is never used while one that can be dated verifies. - First seen. Each result keeps when kardinal first saw each attestation of its type for the image (firstSeen, by payload digest, the 16 newest): an attestation that is listed again, or pushed again, keeps the date it was first seen. - Status. Each result records verifiedAt, statementTime, timeSource, datedAt, firstSeen, staleAt (its age base plus maxAge) and stale. The reconciler comes back at staleAt and sets stale. The phase stays Verified, and a gate reads attestations.<name>.stale, true when any image's result is stale. - A newer attestation. While a result is stale, the image's referrers are read again every quarter of maxAge, at least every hour and at most every 5 minutes. The attestation that verifies and stays fresh longest (the latest staleAt) replaces the result, and the gates that read it are evaluated again. It is picked by age, not by its place in the referrers: a registry lists referrers in no defined order, and key-signed scans have no signing time to sort by. For a 1h maxAge that is at most 4 registry reads per hour per stale version; nothing is read before a result goes stale. - Required. A required attestation that is already stale when the version is checked is waited for like a missing one, until the timeout (status.reason: AttestationStale). - A new vulnerability published after the scan is still not seen until a new scan is attached: maxAge is what makes the scanner run again.

    Signed commits¶

    With commits.requireSigned, the config version's configRef.commitSHA must be the full 40- or 64-character SHA (a short one fails the version). The commit is checked with the Pipeline's SCM provider: the ScmProvider or ClusterScmProvider of its spec.git.providerRef (several SCM providers), otherwise the controller's --scm-provider. The repository must be on that provider's host (its apiURL, or --scm-api-url; api.github.com is github.com). The SCM is asked about that exact commit, and the SHA it answers for must be the same.

    With a providerRef, the provider is resolved as for the Pipeline's PRs: its own token, the same UID the Bundle's Graph was built with, a ClusterScmProvider's allowedNamespaces, and its allowedRepositories, which must allow the config repository (configRef.gitRepo, or spec.git.url). A provider that is gone, was created again, or does not allow the namespace or the repository fails the ImageVerification with the reason; it never falls back to the controller's provider. So does a provider whose apiURL is refused (not a URL, or http:// without scm.providersAllowInsecureHTTP). A provider that cannot be used yet (its token Secret missing or not labeled kardinal.io/referenceable) is retried until the policy's timeout.

    The SCM's verdict is about the key it holds for the signer; allowedSigners narrows it to the people you accept, by login or email as the SCM reports the verified signer. Forgejo reports the signer's login in signer.name, Gitea in signer.username; kardinal reads either, and looks the login up (GET /api/v1/users/{login}) to tell a person from the instance key. Give the controller's token the read:user scope; without it the lookup is made anonymously, so a private user's signature reads as the instance key and is refused. GitLab is matched on the key owner's verified email (for SSH signatures, whose response names the key only by a title its owner chose, on the commit's committer email, which GitLab checked against the key's owner); it reports no full GPG fingerprint, so keys are not matched.

    Commits signed by the platform rather than a person are refused unless allowedSigners lists the platform identity explicitly:

    Platform Identity Which commits
    GitHub web-flow web UI edits, merges, squash merges and reverts, signed with GitHub's key
    GitLab gitlab-system commits GitLab created and signed itself (status verified_system: web UI, API)
    Forgejo / Gitea forgejo-instance commits signed with the instance key (repository.signing): a verified signature whose signer is not a user of the instance (GET /api/v1/users/{name} answers 404), or one named in --scm-instance-signers (Helm scm.instanceSigners: the instance's SIGNING_NAME or SIGNING_EMAIL), or, for a Pipeline's ScmProvider or ClusterScmProvider, in its spec.instanceSigners

    To accept PRs merged in the web UI (the usual GitOps flow), list the identity, for example allowedSigners: [web-flow, alice, bob@example.com]. Anyone who can merge through the web UI then gets such a commit, so pair it with branch protection that requires reviews.

    Commit signatures with gitsign¶

    An SCM verifies a signature against a key one of its users registered, so it cannot verify a gitsign signature: a short-lived Fulcio certificate for a workload identity (a CI job, an agent's runner) with its Rekor entry embedded. With commits.authorities, kardinal verifies those itself:

    imageVerification:
  authorities:
    - name: agents
      keyless:
        issuer: https://token.actions.githubusercontent.com
        subjectRegExp: https://github\.com/myorg/agents/\.github/workflows/.+@refs/heads/main
  commits:
    requireSigned: true
    authorities: [agents]
    1. The signed payload and the signature are read from the SCM API: GitHub GET /repos/{repo}/git/commits/{sha}, Forgejo and Gitea GET /api/v1/repos/{owner}/{name}/git/commits/{sha}. Another provider fails the version (GitLab's API returns no payload).
    2. The commit SHA is recomputed from payload and signature, as git hashes the commit, and must be configRef.commitSHA: the SCM cannot answer for another commit.
    3. The CMS signature must be over that payload, by the certificate it carries.
    4. The certificate, the signature and the embedded Rekor entry are verified offline, as for a keyless image: the certificate chains to the authority's Fulcio root and was valid at the Rekor entry's time, the entry's inclusion proof or signed timestamp verifies against the Rekor keys of the trusted root (public good, or trustedRootRef), and the certificate's issuer and subject match the authority.

    A signature without an embedded Rekor entry (gitsign's online mode, before v0.8) is refused, as is a GPG or SSH one. A signature that does not verify fails the version at once: a commit's signature does not change. An SCM that cannot be reached, or an authority that cannot be loaded yet, is retried until the policy's timeout.

    status.commit records method: gitsign, the signer (certificate subject), issuer, authority, and the agent: the AgentIdentity whose signingIdentities match the signer, when exactly one ready, unsuspended AgentIdentity does. A gate reads them as commit.*, for example to require that an agent's version was signed by that agent's own workload:

    expression: 'actor.kind != "agent" || (commit.verified && commit.agent == actor.agent)'

    The same mapping applies to a keyless attestation's signer (attestations.<name>.agent).

    In a compact Graph (above --graph-compact-above environments) it works the same: the root environments' PromotionSteps name the ImageVerification and wait for it, and so do their pre-deploy hooks.

    What it cannot do¶

    • It verifies before promotion, not at deploy time in the target cluster. To enforce signatures on every Pod, whoever deploys it, add admission-time verification there: Sigstore policy-controller or Kyverno verifyImages. A change pushed to the GitOps repository outside kardinal is not verified by kardinal.
    • A verified image is not checked again: a key revoked after the verification is not seen.
    • Images that arrive through a config commit (a configRef whose files change an image) are not image-verified: only the Bundle's spec.images are. Use commits.requireSigned for config versions, and admission-time verification for images in config changes.
    • Without commits.authorities, commit signatures are taken from the SCM's own verification (the keys its users registered), not checked against a key in the policy. With it, only gitsign (Sigstore) signatures are accepted; GPG and SSH signatures need the SCM path.
    • A gitsign commit is read only through the SCM API (GitHub, Forgejo, Gitea); there is no git fetch fallback for other providers yet (#2109).

    Permissions¶

    The controller reads the key, trusted-root and registry Secrets labelled kardinal.io/referenceable: "true" (it already has get on Secrets), lists agentidentities (for signingIdentities; it already has list) and writes imageverifications; the Graph ServiceAccount creates them.
