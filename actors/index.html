    Agents and the verified actor¶

    New in v0.12.0

    v0.11.0 and earlier do not have this. The changelog lists every v0.12.0 change.

    Every version, approval and gate override kardinal records says who made it, and for whom: the actor. A person, a CI bot, kardinal itself, or an AI agent with the person who answers for it. The API server verifies the actor when the record is written, so nobody can write a record in someone else's name, and an agent cannot pass as a person.

    $ kardinal history checkout
VERSION          ACTION    ACTOR                          ENV    PR    DURATION   TIMESTAMP
1.5.0 (ck-7f3)   promote   agent fixer for alice          uat    #42   ...        2026-10-14 09:12
1.4.0 (ck-2a1)   promote   bob                            prod   #40   4m         2026-10-13 16:03
1.3.2 (ck-9d0)   promote   kardinal (subscription)        test   --    1m         2026-10-13 11:47

    The actor¶

    Field Verified What it is
    kind yes human, agent, bot (a ServiceAccount that is not a registered agent, or the Bundle API's static token) or controller (kardinal acting on its own)
    principal yes The username the API server authenticated
    agent yes The agent's name (its AgentIdentity), when kind is agent
    sponsor yes The person who answers for the agent, when kind is agent, as registered when the record was written
    via yes ui or api when kardinal wrote the record for a caller it authenticated; subscription or auto-rollback for its own versions
    asserted.model, asserted.session, asserted.client no What the client says about itself. Recorded as written, shown labelled "asserted", never used to decide anything

    The actor is in each record's own spec, and never changes after the record is written:

    Record Field
    Version (Bundle) spec.actor
    Approval spec.actor
    Gate override spec.overrides[].actor
    AuditEvent spec.actor

    A record written before v0.12, or with kubectl without a stamp, has no actor. kardinal shows it by its kardinal.io/created-by (or the Approval's spec.user), and its kind is unknown.

    How the actor is verified¶

    The chart's <release>-actor ValidatingAdmissionPolicy checks every new version and Approval, and <release>-actor-overrides every gate override. They read the agent registry from the AgentIndex named after the release, which the controller builds from the AgentIdentities, and admit a stamp only when it says exactly what the requester is:

    • the principal is the requester's username;
    • the kind is agent when the requester, or one of its groups, is a registered agent, bot for any other ServiceAccount, and human otherwise;
    • an agent's agent and sponsor are the ones registered;
    • only kardinal's controller sets via.

    Until the controller has built the index (kubectl get agentindex shows its Ready condition), the policies refuse every version, Approval and override they check, people's included, with "kardinal's agent index is not ready yet", and the UI API and the Bundle API answer 503: the registry fails closed. That lasts a few seconds after an install or an upgrade; the controller reports ready only once the index is. Writes the policies do not check go on meanwhile: kro's gate instances, and the versions kardinal creates itself (automatic rollbacks, Subscriptions), so promotions already under way keep moving.

    The chart creates the index, empty, before the policies (Helm installs it first), and the <release>-agent-index policy lets only the controller delete it (one by one or with kubectl delete agentindexes --all) or write its status. If it is deleted anyway, with that policy's binding removed, the controller recreates it with the release's Helm labels and annotations, so the next helm upgrade adopts it; until the chart has created it in the first place, the controller waits for it. The API server refuses every write a policy with params matches while its param is missing ("no params found for policy binding with Deny parameterNotFoundAction"), before the policy's own rules run, so a missing index would stop kro's and kardinal's writes too. helm uninstall leaves the index (helm.sh/resource-policy: keep); delete it afterwards with kubectl delete agentindex <release>.

    Who paused, resumed or released a Pipeline, and who rejected a Bundle, is checked the same way: the write that records it carries the label kardinal.io/actor-check: "true" (kardinal pause, resume, hold, release-hold, reject, the UI and the MCP tools set it), and the <release>-actor-record-marker policy refuses such a write without it, by anyone but the controller, when the record carries an actor stamp (one without a stamp has nothing to check). So <release>-actor-records converts the index only for those writes, not for the controller's many Pipeline and Bundle updates. The label stays on the object; later writes to it pay that cost too.

    A gate override is checked when the write that adds it carries the label kardinal.io/override-check: "true": kardinal override and the UI set it, and the <release>-override-marker policy refuses an override added without it, by anyone but the controller. The label lets the API server leave kro's re-applies of a gate instance that was never overridden out of <release>-actor-overrides, which converts the whole index for each request it matches. The label stays on a gate once it has been overridden, so kro's later re-applies of that instance are matched and pay that cost; overrides are rare, so few gates carry it. Add it yourself if you write spec.overrides with kubectl, scripts or GitOps tools: the refusal names it.

    An agent must stamp what it writes; a person or a bot may leave the stamp out, as before v0.12. An agent that is suspended, or out of its scope, is refused. kardinal sets the stamp for you: create bundle, ship, promote, rollback, approve and override read your identity and the agent index, and refuse an agent out of its scope before writing anything. The UI and the Bundle API stamp for the caller they authenticated, with the same rules.

    A refusal says what to write:

    $ kubectl --as=system:serviceaccount:ci:fixer create -f bundle.yaml
Error from server (Forbidden): ... you are agent fixer (sponsor alice@example.com): set actor
{kind: agent, principal: system:serviceaccount:ci:fixer, agent: fixer, sponsor: alice@example.com};
kardinal sets it for you

    To record what the client asserts about itself, set it in the environment of the kardinal command:

    export KARDINAL_ACTOR_MODEL=claude-opus-5 KARDINAL_ACTOR_SESSION=run-7f3c2a
kardinal ship checkout --image ghcr.io/acme/checkout:1.5.0

    KARDINAL_ACTOR_CLIENT names the tool. Unset variables record nothing.

    Register an agent¶

    An AgentIdentity is cluster-scoped: only cluster-wide admins write it (cluster admins, and holders of <release>-admin through a ClusterRoleBinding).

    apiVersion: kardinal.io/v1alpha1
kind: AgentIdentity
metadata:
  name: fixer
spec:
  description: Fixes failing builds and ships the fixes to test.
  subjects:                     # who is this agent: 1 to 16
    - kind: ServiceAccount
      namespace: ci
      name: fixer
    - kind: Group               # every member of the group is this agent
      name: oidc:agents-fixer
  sponsor:
    user: alice@example.com     # a person: never a ServiceAccount
    team: payments              # shown, not used by policy
  scope:
    namespaces: ["payments-*"]  # exact names, or a prefix ending in "*"; empty: nowhere
    pipelines: ["checkout"]     # versions only for these Pipelines; empty: all
    environments: ["test", "uat"]  # approvals and overrides only here; empty: all
  autonomy: approve             # auto | approve | deny: the most the agent may do alone

    $ kubectl get agentidentities
NAME    SPONSOR             AUTONOMY   SUSPENDED   READY   AGE
fixer   alice@example.com   approve    false       true    2m

    The AgentIdentity is ready unless it is invalid:

    • SubjectConflict: another AgentIdentity already lists one of its subjects. The older one keeps it: a principal is never two agents.
    • InvalidSponsor: its sponsor is itself an agent.
    • InvalidSigningIdentity: a signingIdentities[].subjectRegExp does not compile.
    • IndexFull: the agent index is past its size bound (1 MiB of entries, about 5,000 AgentIdentities of one subject each, blocked ones included; kardinal supports up to 4,000, see Scale and limits). The whole index is then not Ready, and kardinal refuses every write the actor policy checks until AgentIdentities or subjects are removed.

    The subjects of an AgentIdentity that is not ready are refused, with its reason, rather than treated as people.

    The index records how full it is: status.bytes (its entries, as the bound counts them) and status.maxBytes, and a NearFull condition, True from 80% of the bound, whose message says how many more AgentIdentities of the average size fit. kubectl get agentindex shows them; the chart's KardinalAgentIndexNearFull and KardinalAgentIndexFull alerts fire on the kardinal_agent_index_bytes and kardinal_agent_index_max_bytes metrics (Monitoring).

    scope.pipelines applies to the versions an agent creates and the gate overrides it records (a gate instance names its Pipeline). An Approval is checked against scope.namespaces and scope.environments only: it names a Bundle, not a Pipeline, so give an agent that approves a namespace of its own Pipelines. autonomy (default approve) is the most the agent may do alone: with approve, each of its versions waits in every environment until a person approves it (Autonomy per environment).

    Registering an agent decides how kardinal records it. What it may do is still decided by RBAC: give its ServiceAccount the chart's roles as for anyone else (User roles).

    Signing identities¶

    The actor stamp verifies who created a version. The commit it promotes, and the provenance of its images, were signed by whoever ran the job. spec.signingIdentities lists the Sigstore (Fulcio) certificate identities that are the agent's own workload, so a verified signature can name the agent:

    spec:
  signingIdentities:            # up to 8
    - issuer: https://token.actions.githubusercontent.com
      subjectRegExp: https://github\.com/myorg/agents/\.github/workflows/fixer\.yml@refs/heads/.+

    Each entry has the OIDC issuer, and exactly one of subject and subjectRegExp (which must match the whole subject). When a config commit's gitsign signature, or a keyless attestation, verifies with a certificate that matches the identities of exactly one ready, unsuspended AgentIdentity, its ImageVerification records that agent: commit.agent and attestations.<name>.agent in a gate. A signer that matches none, or several, records no agent (the second with a note naming them in status.commit.message). The mapping is made when the signature verifies; suspending the agent afterwards shows through agent.*, which a gate reads at each evaluation:

    expression: 'actor.kind != "agent" || (commit.agent == actor.agent && agent.registered && !agent.suspended)'

    Suspend or remove an agent¶

    Set spec.suspended: true to stop an agent at once: every write by its subjects that the actor policy checks is refused, and nothing it already wrote changes. The change takes effect within seconds, when the controller rewrites the index.

    An AgentIdentity can be deleted only once it is suspended. Deleting it turns its ServiceAccount subjects into bots and its users and groups into people, so remove their RBAC first.

    Who can read the registry¶

    Every authenticated user can read AgentIdentities and the AgentIndex (actors.directory.public: true, the default): kardinal reads the index to stamp what you write, and the UI shows who sponsors an agent anyway. With false, bind the <release>-agent-directory-reader ClusterRole to the people and agents who use kardinal; a caller who cannot read the index writes no stamp, which is refused for an agent.

    Where the actor shows¶

    • CLI: kardinal history has an ACTOR column, and kardinal why names who made the version waiting. -o json carries the actor object.
    • UI: the stage drawer says who shipped the version ("Shipped by agent fixer for alice@example.com"), with the asserted model apart.
    • PR evidence: the "Created by" line is the actor (Read PR evidence).
    • Audit: each AuditEvent names its actor, and every write through the UI API and the Bundle API is an APIWrite AuditEvent naming the caller and the route. kardinal audit export writes them as JSON lines or OCSF events for a SIEM (Audit logging).

    What this does not protect against¶

    • A stolen agent credential is the agent: suspend the AgentIdentity and revoke the credential.
    • An agent nobody registered is a person (an OIDC user) or a bot (a ServiceAccount).
    • Asserted fields are claims.
    • The index is rebuilt after each AgentIdentity change; while the controller is down, the index is stale but stays in place.
    • Anyone with edit or admin in the controller's namespace can act as the controller.
    • An agent that holds the UI's or the Bundle API's static token writes as that token: a bot named kardinal-ui or bundle-api, outside its suspension and scope. Give agents a Kubernetes identity and TokenReview mode instead.

    The design, with the options considered for each decision, is in Actors.
