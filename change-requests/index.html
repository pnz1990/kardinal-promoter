    Change Requests¶

    New in v0.13.0 (unreleased)

    v0.12.0 and earlier do not have ChangeRequests. The changelog lists every change since v0.12.0.

    Many teams may not change production without an approved change request: a ticket in ServiceNow or Jira that a change advisory board (CAB) or a release manager approves. A ChangeRequest lets kardinal open that ticket for a promotion, or track one someone already opened, and lets a gate wait until it is approved:

    apiVersion: kardinal.io/v1alpha1
kind: PolicyGate
metadata:
  name: cab-approval
  namespace: checkout
  labels:
    kardinal.io/scope: team
    kardinal.io/applies-to: prod
spec:
  expression: 'changeRequests["prod-change"].state == "approved" && !changeRequests["prod-change"].stale'
  message: "prod needs an approved change request"
  recheckInterval: 1m

    How it works¶

    A ChangeRequest with spec.perPromotion: true is a template, like a per-promotion MetricCheck:

    1. Each Bundle's Graph creates an instance of the template for every environment whose gates read changeRequests.<name> and that the template applies to (spec.appliesTo). The instance is created once every upstream environment is Verified, so no ticket is opened for a version that never reached the gate.
    2. The ChangeRequest controller opens the ticket (mode: open) or reads its key from the promotion (mode: link), then reads the ticket's state every pollInterval and writes it to the instance's status.
    3. The gate reads the instance's status as changeRequests.<template name>. It never calls the ticketing system itself.
    4. When the Bundle stops promoting the controller stops reading the ticket: once it is Verified or Failed the Graph sets spec.suspend on the instance, and once it is Superseded or Rejected (or gone, or re-created under the same name) the controller sees that on the Bundle itself and the instance's Ready condition says VersionFinal. kardinal does not close or cancel the ticket.
    apiVersion: kardinal.io/v1alpha1
kind: ChangeRequest
metadata:
  name: prod-change            # gates read changeRequests["prod-change"]
  namespace: checkout          # the Pipeline namespace
spec:
  perPromotion: true
  appliesTo: [prod]            # unset: every environment whose gates read it
  provider: servicenow         # servicenow | jira
  mode: open                   # open (default) | link
  servicenow:
    instanceURL: https://example.service-now.com
    credentialsSecretRef: {name: snow-kardinal, key: token}
    scheme: basic              # basic (user:password) | bearer (OAuth token)
    type: normal               # normal | standard | emergency
    template:
      short_description: "Promote {{ pipeline.name }} {{ bundle.version }} to {{ environment.name }}"
      assignment_group: payments-cab
  pollInterval: 1m             # default 1m, minimum 30s
  timeout: 24h                 # status.timedOut after it; "0" for none

    The instance is named <template>-<environment>--<bundle> (hash-shortened when too long) and labelled kardinal.io/change-request-template, kardinal.io/bundle, kardinal.io/environment and kardinal.io/bundle-uid:

    kubectl get changerequests -n checkout
# NAME                          PROVIDER     TICKET       STATE      AGE
# prod-change                   servicenow                           3d
# prod-change-prod--checkout-7f3c2a   servicenow   CHG0031337   approved   12m

    Ticket templates¶

    template holds the fields the ticket is created with, as strings. The placeholders are the per-promotion MetricCheck ones: {{ bundle.name }}, {{ bundle.version }}, {{ bundle.imageTag }}, {{ bundle.imageDigest }}, {{ bundle.commitSHA }}, {{ pipeline.name }}, {{ environment.name }} and {{ namespace }}. A value is put into the field as text: control characters are dropped and it is cut to 256 bytes. An unknown placeholder is left as it is.

    Credentials¶

    credentialsSecretRef names a Secret key in the ChangeRequest's namespace. The Secret must be labelled kardinal.io/referenceable: "true", as for MetricChecks and NotificationHooks: its owner agrees to have it sent to the address whoever writes the ChangeRequest chooses. Give kardinal a credential that may create and read changes, not one that may approve them. Every request goes through the controller's egress guard: loopback, link-local and cloud metadata addresses are refused (condition Refused), and with --egress-allowlist only the listed destinations are reached. Cluster and other private addresses are allowed by design, so an in-cluster ticketing proxy works; narrow them with the allowlist or a NetworkPolicy (Outbound requests to user URLs).

    ServiceNow¶

    kardinal uses the Table API: it creates and reads change_request records, and reads their approvals from sysapproval_approver.

    Call Request
    Open POST /api/now/table/change_request with the template's fields, type (spec.servicenow.type), correlation_id and correlation_display: kardinal
    Find (before every create) GET /api/now/table/change_request?sysparm_query=correlation_id=<key>^sys_created_by=<integration user>^ORDERBYsys_created_on
    Read GET /api/now/table/change_request/<sys_id>, or by number for a linked ticket
    Approvers GET /api/now/table/sysapproval_approver?sysparm_query=sysapproval=<sys_id> (a refusal leaves them out)

    Only kardinal's own changes are adopted. Find returns a change only when the integration user created it (sys_created_by), so someone who may create changes cannot plant one with the promotion's correlation id and approve it themselves. The answer must also carry the promotion's correlation_id. An answer that does not means the instance ignored part of the query (ServiceNow skips a condition it cannot apply) and returned another promotion's change: it is not adopted, and no change is created either, since the search cannot show whether this promotion's exists. The instance reports ProviderError with reason ProviderIgnoredFilter and retries after five minutes. With scheme basic the integration user is the credential's user; with bearer set spec.servicenow.integrationUser to the user_name the token acts as (the CRD requires it).

    instanceURL is https://<host> only: a path, query, fragment or user name is refused (by the CRD and by the controller), since every ticket URL kardinal records is built from it. A change whose number is not capitals then digits (CHG0031337) is not read: its number would appear in the PR body and the receipt.

    The template cannot set type, correlation_id or correlation_display. correlation_id holds kardinal- and 32 hex characters of the promotion's correlation id's SHA-256, because the field holds 100 characters. Give the integration user a role that may create and read change_request and read sysapproval_approver (for example itil), and no right to approve.

    The state is read from state and approval, mapped with the default Change Management state model:

    ServiceNow state
    approval is rejected rejected, always: no states map overrides it
    state Canceled (4) cancelled
    state Closed (3) or Review (0) closed
    approval is approved and state Scheduled (-2) or Implement (-1) approved
    anything else (New, Assess, Authorize, approval requested) pending

    An instance with its own state model maps its values in spec.servicenow.states, by raw value or display name, before the defaults (and after a rejected approval, which always wins). A value mapped to approved counts only when approval is approved; otherwise it reads pending, so a map can never approve what nobody approved:

    servicenow:
  states:
    "-3": approved        # this instance's approved changes wait at Authorize
    "Implement": closed

    For a linked ticket, link.requireField names a change_request field. A reference field such as cmdb_ci matches by its sys_id or its display value. providerState is the state and approval as ServiceNow displays them (Scheduled / Approved).

    An instance behind an internal CA. Put the CA certificates (PEM) in a ConfigMap in the release namespace and set changeRequest.caBundle.configMap (and .key, default ca.crt). The controller then trusts them, besides the system roots, for ChangeRequest calls only (--change-request-ca-file).

    Jira¶

    kardinal uses the Jira REST API: version 3 on Jira Cloud (the default) and version 2 on Jira Data Center (spec.jira.apiVersion: "2").

    spec:
  provider: jira
  jira:
    baseURL: https://example.atlassian.net
    credentialsSecretRef: {name: jira-kardinal, key: token}   # email:API-token (Cloud), or a PAT
    scheme: basic                  # basic on Cloud; bearer for a Data Center personal access token
    project: CHG                   # required: issues are opened, searched and linked only here
    linkProjects: [OPS]            # optional: further projects a linked issue may be in
    issueType: Change              # default Task
    template:
      summary: "Promote {{ pipeline.name }} {{ bundle.version }} to {{ environment.name }}"
      description: "Opened by kardinal for {{ namespace }}"
    approvedStatuses: [Approved]   # or, unset, approvedStatusCategory (default done)
    approvedResolutions: [Done]    # a resolved issue counts as approved only with one of these
    rejectedStatuses: [Declined]
    cancelledResolutions: ["Won't Do"]   # the default
    Call Request
    Open POST /rest/api/<v>/issue with the template's fields, project, issuetype and the correlation label
    Find (before every create) POST /rest/api/3/search/jql (v2: /rest/api/2/search), JQL project = "<project>" AND labels = "<key>" AND creator = currentUser() ORDER BY created ASC, then GET /rest/api/<v>/myself to check the creator
    Read GET /rest/api/<v>/issue/<id>, or by key for a linked issue

    Only kardinal's own issues are adopted. Find returns an issue only when the integration account created it (creator = currentUser(), checked again against /myself), so someone who may create issues cannot plant one with the promotion's label and move it to an approved status themselves. The creator, not the reporter, decides: Jira sets the creator and nobody can change it, while Modify Reporter and Service Management's "raise on behalf of" set the reporter to any account. The answer must also carry the promotion's label: a site that ignored part of the JQL and returned another promotion's issue gets ProviderError with reason ProviderIgnoredFilter, and nothing is adopted or created until a search answers correctly (retried after five minutes).

    The template cannot set project, issuetype or labels. The correlation label is kardinal- and 32 hex characters of the correlation id's SHA-256. On API version 3 the description is sent as an Atlassian Document Format paragraph. Give the account permission to create and browse issues in the project, and no right to move them through the approval step.

    Jira has no approval model outside Jira Service Management: teams model approval as a workflow status. The state is read in this order:

    Jira state
    status in rejectedStatuses rejected
    resolution in cancelledResolutions (default Won't Do) cancelled
    approvedStatuses set: status in it, unresolved or resolved in approvedResolutions approved
    approvedStatuses unset: status category approvedStatusCategory (default done) and resolved in approvedResolutions approved
    resolved in anything else (Duplicate, Declined, a resolution nobody configured) closed: never approved
    anything else, an unresolved done issue included pending

    Only what you configure approves. Without approvedStatuses, the status category approves only with a resolution listed in approvedResolutions: many workflows move an issue to a done status such as Declined or Rejected without setting a resolution, and that must never release prod. With no approvedResolutions either, nothing is approved; list the approved statuses, as in the example above. An issue outside project and linkProjects is refused (by its key before any request, and by its own project field after a read), so a link cannot point at another project's approved issue. A rejected or cancelled issue is often in the done category too, which is why those come first. providerState is the status, and the resolution when there is one (Done / Won't Do). Jira issues have no approvers: approvers stays empty. For a linked issue, link.requireField names a field (components, customfield_10010, ...): an option or user matches by its value or name, a list when one element matches.

    Webhook trigger¶

    kardinal polls each ticket every pollInterval, which is correct with no inbound path at all. A ticketing system can also tell kardinal that a ticket changed, so the gate opens within seconds of the approval instead of at the next poll:

    spec:
  perPromotion: true
  webhook:
    secretRef: {name: cr-hook}   # labelled kardinal.io/referenceable=true; key token, 16+ characters

    POST https://<controller webhook address>/webhook/changerequests/<namespace>/<template>
X-Kardinal-Token: <token>

    Send the token in the X-Kardinal-Token header. A sender that cannot set headers can put it in the last path segment instead (.../<template>/<token>), but proxies and access logs record paths, so prefer the header.

    Generate the token with a random source and put it in the Secret the template names. It must be at least 16 characters; 32 random bytes as hex is a good default:

    kubectl -n checkout create secret generic cr-hook \
  --from-literal=token="$(openssl rand -hex 32)"
kubectl -n checkout label secret cr-hook kardinal.io/referenceable=true

    Give the same value to ServiceNow or Jira and to no one else: whoever has it can make kardinal re-read the template's tickets (never approve them).

    Rotate it by writing a new value into the Secret and then updating the sender. The receiver reads the Secret on every request, so the new token works at once and the old one stops at once. Until the sender has the new value its triggers get 401, and polling still reads the tickets, so a rotation delays a promotion by at most one pollInterval:

    kubectl -n checkout create secret generic cr-hook \
  --from-literal=token="$(openssl rand -hex 32)" --dry-run=client -o yaml | kubectl apply -f -

    The request makes every instance of the template read its ticket at once (the kardinal.io/refresh annotation; status.observedRefresh records the trigger it answered). Its body is never read for state: the state always comes from the ticketing system's API, so a forged or replayed body changes nothing, and a lost trigger only means the next poll reads the change. A wrong token, a template without webhook, and a template that does not exist all get the same 401; the token is compared in constant time and never logged. A trigger never overrides a provider's Retry-After (status.retryAt). The receiver answers 429 past a coarse limit of 50 requests a second across all templates, checked before anything is read, and past five valid triggers a second per template; requests with a wrong token never use up a template's budget. The coarse limit comes before the token check on purpose: it keeps unauthenticated requests from turning into ChangeRequest and Secret reads on the API server. A flood of such requests can therefore make your valid triggers wait their turn (429), but it cannot change any state, and polling still reads every ticket each pollInterval, so the only cost is latency.

    • ServiceNow: a business rule on change_request (after update, when approval or state changes) that sends an outbound REST message to the URL with the X-Kardinal-Token header. Restrict it to the changes kardinal opened with the condition correlation_display is kardinal.
    • Jira: a webhook (Settings, System, WebHooks) on "Issue updated" with the URL (Jira webhooks set no custom headers, so the token goes in the path), filtered by JQL to the project, for example project = CHG AND labels ~ "kardinal-*".

    The URL carries the token, so expose the controller's webhook port only over TLS, as for Subscription webhooks.

    The gate¶

    changeRequests.<name> has state, ticket, url, stale, timedOut, verified, approvers and providerState (CEL context).

    state Meaning
    "" No ticket yet: the instance does not exist (its upstreams are not Verified), or has not opened or found its ticket
    pending The ticket waits for approval
    approved Approved, and not yet implemented or closed
    rejected Rejected
    cancelled Cancelled
    closed Closed or in review
    unknown The provider's state maps to none of these, the linked ticket was not found, or the last reading is stale

    A reading is fresh for two poll intervals. After that, stale is true and state reads unknown, so state == "approved" alone already blocks when the ticketing system cannot be reached. A name with no template is an evaluation error, and the gate blocks. While it blocks, the gate's reason names the ticket:

    expression false; change request prod-change: ticket CHG0031337 is pending (Authorize / requested)

    Org gates (templates in an org policy namespace) read the org namespace, where the Graph creates no instances: their changeRequests entries never have a ticket, so they block.

    Open or link¶

    • open (default): kardinal opens the ticket. It writes the promotion's correlation id (kardinal:<namespace>/<bundle>/<environment>/<bundle UID>) into the ticket, and before every create it searches for a ticket with that id and adopts it. The create is first recorded in status.pendingCreate, so a controller restart or a lost response never opens a second ticket. A Bundle deleted and created again under the same name has a new UID, so it gets a new ticket.
    • link: kardinal never opens a ticket. It reads the key from the promotion and tracks that ticket:
    spec:
  mode: link
  link:
    from: approvalField        # approvalField | bundleLabel | bundleAnnotation
    name: ticketID             # the approval field, label or annotation
    requireField:              # optional: the ticket's field must have this value
      name: cmdb_ci
      value: checkout

    approvalField reads a structured approval field of the environment's counted approvals: kardinal approve checkout prod --field ticketID=CHG0031337. Approvals that do not count give no key, and two counted approvals with different keys are refused (condition ProviderError). bundleLabel and bundleAnnotation read the Bundle CI created.

    A linked ticket is verified when it carries the promotion's correlation id, or when all of these hold:

    • its link.requireField field has that value;
    • it was created after the Bundle: an older ticket, approved for an earlier version, cannot be this version's;
    • no other ChangeRequest holds it from earlier: one that opened it, or one that linked it first (status.linkedAt). One ticket approves one promotion.

    Holders are counted across the cluster: a team that links a ticket key first, from its own approval fields, leaves another team's later link of the same key unverified. That fails closed (it can delay a promotion, never approve one); use requireField values that belong to your service, and prefer mode open, whose tickets carry the promotion's correlation id.

    Otherwise status.verified and changeRequests.<name>.verified are false, verifiedReason says which rule failed, and the ChangeRequestLinked record says so: an approver could have linked an unrelated, old or already used approved ticket. Require it in the gate:

    expression: 'changeRequests["prod-change"].state == "approved" && changeRequests["prod-change"].verified'

    Status and records¶

    Field Meaning
    status.ticket key, id (sys_id or issue id) and url
    status.state, status.providerState The normalised and the provider's own state
    status.approvers The ticket's approvers, when the provider reports them
    status.observedAt, status.validUntil The last reading, and when it goes stale (two poll intervals later)
    status.timedOut spec.timeout has passed since the instance started
    status.retryAt After an error, when the next request is sent
    status.conditions Ready, Stale, CredentialsInvalid, Refused (egress), ProviderError

    The instance writes AuditEvents ChangeRequestOpened, ChangeRequestLinked, and, the first time the ticket is read so, ChangeRequestApproved and ChangeRequestRejected (kardinal get auditevents --pipeline checkout --env prod, or kubectl get auditevents -l kardinal.io/action=ChangeRequestApproved).

    In the PR, the receipt and the evidence pack¶

    • The PR. A promotion PR has a ### Change Requests section after the gate table, with one row for each ticket of the version in that environment: the template, the ticket key linked to its URL, the provider, the state (with the provider's own), whether the ticket is the promotion's (yes, or no: and the reason a link was not verified), the approvers and when the ticket was last read. The rows are read when the PR is opened, like the gate table. Text from the ticketing system (approver names, states, keys, reasons) is shown as plain text: HTML, images, links, @ mentions and issue references in it do not render, and directional formatting characters are removed. A custom PR body gets the section with {{ changeRequestsTable }} (Customising the PR).
    • The receipt. kardinalPromotion.changeRequests records each ticket as the step read it when it started, next to its gates: template, instance, provider, key and URL, state, whether it was verified and why, approvers, observedAt and validUntil (Promotion receipts). A ticket closed after the step started stays as the step saw it. The approvals in the receipt carry their structured fields (Approval fields).
    • The evidence pack. changerequests.ndjson holds the instances of the period's versions, and changerequest-templates.ndjson the templates in force at export (Produce an evidence pack).

    Each record names the template by the instance's kardinal.io/change-request-template label. A label value is at most 63 characters, so a longer template name appears cut, with a hash suffix.

    Only kardinal writes an instance: the chart's graph-objects admission policy refuses anyone else (a user with full RBAC, the cluster admin) creating one or changing its status. A template has no kardinal.io/bundle label and is yours to write.

    Limits and errors¶

    • Rate. An instance makes at most two requests per poll interval (a search and a create, or a read and its approvers). At most changeRequest.maxInflight requests run at once in the cluster and changeRequest.maxInflightPerNamespace per namespace (controller flags --change-request-max-inflight, --change-request-max-inflight-per-namespace; defaults 8 and 1); the rest wait, first come, first served.
    • Errors. A failed request keeps the last reading, which goes stale, and sets status.retryAt: one poll interval later, the provider's Retry-After when longer (HTTP 429), and at least five minutes after a refused credential (CredentialsInvalid) or an egress refusal (Refused), so a revoked token causes no request storm.
    • Timeout. status.timedOut is information for the gate's expression (!changeRequests["prod-change"].timedOut); kardinal does not cancel the ticket.
