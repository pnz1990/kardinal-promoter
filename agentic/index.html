    Agentic delivery¶

    New in v0.12.0

    v0.11.0 and earlier do not have this. The changelog lists every v0.12.0 change.

    GitOps Governance for the Agentic Era.

    Coding agents now write and ship a growing share of changes, and a guardrail that lives inside the agent is one the agent can get around. kardinal enforces governance where the change lands: in the cluster, not in the agent. Every promotion kardinal makes passes the same checks, the Kubernetes API server's admission policies and the controller's gates, whoever started it: a person, a CI system or an agent.

    What kardinal enforces today¶

    Everything below is shipped, and applies to an agent exactly as it applies to a person: an agent acts through a Kubernetes identity (a ServiceAccount, or an OIDC user), and Kubernetes RBAC decides what it may do.

    Control What it does Page
    Agents and the verified actor Register each agent with the person who answers for it (AgentIdentity). Every version, approval and override records its actor, verified by an admission policy: a person, a bot, kardinal, or an agent with its sponsor. An agent cannot pass as a person, write outside its scope, or act while suspended. Model and session are recorded as asserted, apart Agents and the verified actor
    Verified identity on approvals, rejections and overrides ValidatingAdmissionPolicies refuse an Approval, a rejection or a gate override that does not name the caller the API server authenticated. Nobody records a decision in someone else's name Verified identity
    The verified creator Each version's kardinal.io/created-by annotation is admitted only in the requester's name and never changes. With TokenReview enabled, the Bundle API records the authenticated caller Require approvals
    excludeAuthor An approval gate with excludeAuthor: true does not count the version's creator, so whoever created a version, an agent included, cannot approve it Require approvals
    Approval quorum required: N distinct approvers from allowedUsers and allowedGroups; a counted reject blocks Require approvals
    CEL gates PolicyGates hold an environment until a CEL rule passes: soak time upstream, metrics, schedule, PR review state, version metadata Gate promotions
    ChangeWindows Cluster-scoped freezes and allowed hours, enforced by the controller for every pipeline whose gates read them; breaking glass is a verified, time-limited, audited override ChangeWindow attributes, Override a gate
    PR evidence Every pull request kardinal opens carries the version's provenance and each gate's result and reason Read PR evidence
    Verify gates A gate waits for verdicts from agents, people or CI on the version in an upstream environment: a quorum, tolerated fails, inconclusive held, retried or failed, a timeout. Agents count only when listed, never on their own party's work. In-cluster agents run as bounded AgentRuns: read-only, a NetworkPolicy, no git credentials, a deadline Verify with agents
    Actor-aware policy Per-environment autonomy for agents' versions (agents: auto, approve or deny), the one-party rule in excludeAuthor (an agent's sponsor cannot approve its work), opt-in agent approvers, and actor.* and agent.* in gate expressions Actor-aware policy
    Freezes kardinal freeze --agents holds every agent's version; --everyone stops the line. Enforced by the controller on every in-flight promotion; break-glass exemptions are verified and audited Freeze agents, stop the line
    Audit trail Append-only AuditEvent records of promotions, rollbacks, supersession, gate results, approvals, overrides, rejections and every UI API and Bundle API write, each naming its verified actor; kardinal audit export writes them as JSON lines or OCSF events Audit logging
    Compliance mapping Which of these records evidences which control of SOC 2, ISO/IEC 27001, NIST SP 800-53, DORA, the EU AI Act and ISO/IEC 42001, and what remains yours to do Map to compliance controls

    A starting point for an agent¶

    Give the agent its own ServiceAccount, bound in the Pipeline namespace to the chart's <release>-promoter ClusterRole, which may create versions but not Approvals (User roles), and gate prod on people:

    apiVersion: kardinal.io/v1alpha1
kind: PolicyGate
metadata:
  name: prod-needs-a-person
  namespace: my-app
  labels:
    kardinal.io/applies-to: prod
spec:
  expression: "true"
  message: "prod needs a release manager who did not create the version"
  approval:
    required: 1
    allowedGroups: [release-managers]
    excludeAuthor: true

    Register the agent with an AgentIdentity that names its ServiceAccount, its sponsor and its scope. A version the agent ships with its own kubeconfig (kardinal ship my-app --image ...) then records it as "agent for ". It promotes through test and uat under the other gates, and waits at prod for a release manager, who cannot be the agent. Restrict who may push to the GitOps repository, so that changes reach the environments through kardinal, and for pr-review environments require the kardinal/gates status check (Gate status check). Do not grant the agent impersonate: whoever may impersonate passes every identity check as whoever they impersonate.

    Connect an agent over MCP¶

    kardinal mcp is a local MCP server for Claude Code, Codex, Cursor and other agents: the read tools (why, status, simulate and more) by default, the write tools with --allow-write, all as the agent's own Kubernetes identity. Text from PRs, commits and people comes labelled as untrusted data. See Connect an agent.
