- **An aborted canary applies `onHealthFailure` at once, and `fail-on-alarm` before the first healthy check** (#2006) — a canary that Argo Rollouts aborted (a failed analysis) is never healthy again, yet the step only counted failed checks and applied `onHealthFailure` at `health.timeout` (10 minutes by default): a broken canary was rolled back that much later. An Argo Rollouts Rollout that is `Degraded` with `status.abort` on the promoted revision is now a Failed result, with `health.type: argoRollouts` and with `argocd` when the Application reports the aborted Rollout, so `onHealthFailure` applies at the first check that sees it. And `bake.policy: fail-on-alarm` applies `onHealthFailure` at the first Unhealthy check also before the first healthy one, as its API documentation said (a target that does not exist yet still waits for the first healthy check); `reset-on-alarm` is unchanged. A `kubectl argo rollouts retry` after kardinal acted does not resume the step: promote the version again. An abort that an earlier release left counts only when the images tell the releases apart, or when Argo Rollouts aborted after the change reached git ([argoRollouts](health-adapters.md#adapter-argorollouts), [Rollback](rollback.md)).
