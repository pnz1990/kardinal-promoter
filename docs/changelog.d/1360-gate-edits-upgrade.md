section: Upgrade
---

- **Gate changes reach the versions in flight** (#1360, #2271) — no action is needed. On the first reconcile after the upgrade from any v0.12.x, the controller renders the Graph of every promoting version again, once and in place. A Graph that was working keeps the same nodes and objects (its PromotionSteps and gate instances); one stuck under #2271 before v0.12.3 gets the gate instance it was missing. Each gate copy then matches its current template and carries its `kardinal.io/gate-template-*` annotations, so a template created, edited, deleted or moved onto other environments (its `kardinal.io/applies-to` label) under v0.12 after a version started reaches that version at the upgrade, recorded as a `GateChanged` AuditEvent that says it happened on upgrade. From v0.12.0, v0.12.1 or v0.12.2 on a kro install with its alpha `CELOmitFunction` feature gate, the gates of a Graph that holds gates both with and without an approval policy are deleted and created again once then; from v0.12.3, which already splits those gates into their own collections, the re-render updates them in place. Later changes reach the versions in flight at once and are recorded the same way. If you relied on an in-flight version keeping an old gate, use `kardinal pause` or `kardinal hold` instead ([When a new or edited gate takes effect](policy-gates.md#when-a-new-or-edited-gate-takes-effect)).
