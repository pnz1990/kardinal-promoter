    1. Problem and scope¶

    Every version is treated the same today. A one-line README change and a 3,000-line database migration written by an agent with two rollbacks this week get the same soak, the same approvals and the same fleet pace. The controller already knows most of what separates them: who made the version (the actor, spec 17), what failed before (Pipeline.status.deploymentMetrics), and the commits the version carries. It does not combine them, and policy cannot read the result.

    # Feature Section

    R2 path.glob(): a CEL function, in the PolicyGate environment and proposed to kro 5
    R3 risk.* CEL variables 6
    R4 Earned autonomy: per-agent change failure rate, rework rate and rollbacks in AgentIdentity.status 7
    R5 Risk-adaptive soak and approvals, in CEL 8
    R6 Fleet wave presets (AWS: 1, 1, 3, 12, rest, with bake times) 9

    Non-goals:

    • A trained or learned model. §2 says why.
    • Reading commit messages, PR text or code content to score. Only paths and line counts are read.
    • An LLM reviewer inside the score. That stage of RADAR maps to a Verdict from an AgentRun (spec 19), which a gate can already require (§2.2).
    • Per-agent budgets (versions per day, concurrent prod promotions). They are a separate v0.14 item; this spec only shares the deployment records with it (§7.2).
    • Error-budget gates (Sloth, Pyrra). A separate v0.14 item.

    Every open question below compares at least three options and records the choice. §16 is the decision table.

    2. Sources: what we take, and what does not transfer¶

    2.1 Diff Risk Score (Meta, arXiv 2410.06351)¶

    Abreu et al., "Moving Faster and Reducing Risk: Using LLMs in Release Deployment" (https://arxiv.org/abs/2410.06351). Diff Risk Score (DRS) predicts the probability that a diff causes a severe incident (SEV). The baseline is a logistic regression on about 12 features chosen from about 100 (§III-A, Table I): added and deleted lines relative to file size (log scale), new files, files modified, the log of the number of files in the diff, how many authors changed those files, a previous SEV in the file and in its folder, whether a high-criticality service is touched, file complexity, language, and the author's history with the file. The paper's gating (§II-C) blocks the riskiest 5% of diffs on weekends, 10% in "yellow" periods and 50% in "red" periods (Black Friday), and lets engineers land a blocked diff by escalating with a standard reason. The baseline caught 18.7%, 27.9% and 84.6% of SEVs at those three levels; risk-aligned LLMs did 1.40x, 1.52x and 1.05x as well (Table IV). The test set had 181,052 diffs and 305 SEVs.

    What we take:

    DRS idea Here
    Size on a log scale (lines, files) The size and files factors use log-spaced bands (4.6)
    Previous SEV in the file and in its folder The history factor: failed deployments that touched the same path class or directory (4.7)
    High-criticality components Path classes with points, matched with path.glob (4.3)
    Gating levels tied to periods (weekend, yellow, red) Tier and percentile combined with schedule.* and ChangeWindows in plain CEL (8.3)
    Blocked changes land through an escalation with a reason The existing gate override (break-glass, with a reason and an AuditEvent)
    Scores and explanations shown to the developer status.factors[] with the points of each factor, in the PR evidence, kardinal why and the UI

    What does not transfer:

    • The model. DRS is trained on Meta's history of diffs and SEVs (305 SEVs in the test set alone). A kardinal installation has tens to thousands of deployments, and its failure labels are DORA signals (a failed health check, a rollback, a rejection), not attributed incidents. A per-installation regression would be fitted on a handful of failures, and Meta's coefficients describe Meta's code. kardinal therefore ships an additive points model with documented defaults (4.6). It is a policy input that an admin can read and tune, not a prediction.
    • LLM scoring. Non-deterministic, needs model I/O, and would read diff content, which an agent can write to steer the result. Excluded from the score.
    • The unit of change. DRS scores one diff at review time in a monorepo. kardinal promotes a version, which can carry many commits, whose source repository the controller may not be able to read, and whose GitOps change is often one image tag. The score is computed over the commit range between what the final environment runs and what the version brings (4.2).
    • Author expertise from git history. The git author is asserted by whoever made the commit. kardinal uses the verified actor kind (spec 17) instead.
    • Percentile thresholds as the primary cut. At Meta's volume a percentile is stable. A Pipeline with 30 deployments a month has a noisy one. Tiers use absolute scores; the percentile is exposed as a variable (6) for teams with volume.

    2.2 RADAR (Meta, arXiv 2605.30208)¶

    Adams et al., "Automating Low-Risk Code Review at Meta: RADAR, Risk Calibration, and Review Efficiency" (https://arxiv.org/abs/2605.30208). RADAR approves low-risk diffs automatically through a funnel: classify the diff by authorship and source (human, deterministic codemod, AI codemod, runbook), eligibility gates, static heuristics, DRS, an LLM review, and deterministic validation. Over 535,000 reviewed diffs its revert rate was one third, and its production incident rate one fiftieth, of non-RADAR diffs. The DRS percentile threshold depends on the source: the safest 5% for humans, 20% for bot sources that are not allow-listed, 50% for allow-listed runbooks. A runbook's eligibility is earned from a 60-day lookback (no production incidents, low revert and rejection rates, a minimum number of landed diffs). Sources have daily landing caps, can be paused when they cause an incident, and have a landing delay that lets a person stop a change. Scope exclusions (prefix and suffix block lists, sensitive configuration) apply before any score.

    What we take:

    RADAR idea Here
    Classify by source before scoring The actor factor from the verified actor kind (4.6)
    Thresholds per source Policies over actor.kind and risk.tier (8)
    Eligibility earned from a lookback with a minimum count Earned autonomy: windowed track record with agent.trackRecordSufficient (7)
    Pause a source that caused an incident AgentIdentity.spec.suspended (spec 17) and freezes (spec 18); policies on agent.rollbacks (7.5)
    Daily caps per source The v0.14 budgets item (out of scope here)
    Path block lists before any score Path classes, including one that forces red (4.3)
    LLM review stage A verify gate fed by an AgentRun Verdict (spec 19), required by tier (8.2)
    Deterministic validation and a landing delay Health checks, bake, MetricChecks; soak scaled by tier (8.1)

    What does not transfer: RADAR approves code review, before merge. kardinal acts after the artifact is built, on its way through environments, and cannot see test results or review comments, only promotion outcomes. RADAR's outcome evidence is observational (the paper's threats-to-validity section), so its numbers justify the shape, not any default here.

    2.3 AWS waves (Builders' Library)¶

    Clare Liguori, "Automating safe, hands-off deployments", Amazon Builders' Library (2020), now at https://builder.aws.com/content/3ErTKQOTKc5NIw031UePBPxTQ6I/automating-safe-hands-off-deployments (the former aws.amazon.com/builders-library/automating-safe-hands-off-deployments/ redirects there). Production is deployed in waves of increasing size: one Region with low traffic, then one Region with high traffic, then three Regions, then up to 12, then the rest; "we can deploy to more and more Regions in parallel in the same wave" once the early waves give confidence. Each wave starts with a one-box stage. Bake times are "at least one hour after each one-box stage, at least 12 hours after the first regional wave, and at least two to four hours after each of the rest of the regional waves", and the bake "includes requirements to wait for a specific number of data points in the team's metrics". During the bake "the deployment is automatically rolled back if the team's high-severity aggregate alarm goes into the alarm state". Deployments avoid nights, weekends and holidays. Used in §9.

    2.4 DORA definitions¶

    From https://dora.dev/guides/dora-metrics/: change fail rate is "the ratio of deployments that require immediate intervention following a deployment"; deployment rework rate is "the ratio of deployments that are unplanned but happen as a result of an incident in production". The controller already computes the first, with an exact definition of a deployment and a failure (pkg/reconciler/pipeline/metrics.go:316-498, api/v1alpha1/pipeline_types.go:1485-1508). §7 reuses those definitions for agents.

    4. ChangeRisk¶

    4.1 Where the score is computed¶

    Mechanism For Against
    (a) The PolicyGate reconciler computes risk while it builds the gate context No new CRD Git or SCM I/O in the gate hot path (AGENTS.md anti-pattern); recomputed per gate and per recheck; no record
    (b) The translator computes it when it builds the Graph Available before any node exists The translator would do I/O; a Graph rebuild would re-score
    (c) A ChangeRisk owned node per Bundle, scored by its reconciler from a Job's output I/O out of the controller and off the hot path; one immutable record that evidence and receipts can cite; the ImageVerification shape (pkg/graph/imageverify.go:180-219) One more CRD and a Job per Bundle

    Choice: (c).

    4.2 Where the diff comes from¶

    The diff is the change between what the final environment runs now and what the version brings:

    • Image Bundle: the application source, base..head, where head is spec.provenance.commitSHA and base is the commit of the version the final environments run.
    • Config Bundle: the GitOps DRY repository (spec.configRef.gitRepo or the Pipeline's spec.git.url), base..head of configRef.commitSHA.
    • Mixed: both, summed; each part recorded.

    base is chosen by the ChangeRisk reconciler before it creates the Job: for each final environment (finalEnvironments, pkg/reconciler/pipeline/metrics.go:237, every fleet target included), the newest Bundle Verified there; among those, the oldest. That is the largest diff any production target will receive. It is recorded in status.base with the environments it came from. No base (a first deployment, or the base Bundle has no commit) gives factor baseMissing.

    Options for reading it:

    Mechanism For Against
    (a) The PromotionStep's own git clone (pkg/steps/steps/git_clone.go) No new clone That clone is the GitOps repository: for an image Bundle the diff is one tag. It runs in the first environment's step, after the score is needed, and in the controller process
    (b) A Job owned by the ChangeRisk, as RenderRun runs kardinal-render (pkg/reconciler/renderrun, pkg/renderjob): it fetches base and head and diffs the trees Full fidelity for any number of files; one implementation for every git host; sandboxed (no controller credentials, a NetworkPolicy, limits); the result is read from the Pod's termination message as RenderRun does (pkg/renderjob/renderjob.go:41-44,154-184) A Pod per Bundle (seconds to minutes); clone size; the source repository's credentials must be in the namespace
    (c) The SCM compare API from the ChangeRisk reconciler (GET /repos/{o}/{r}/compare/{base}...{head} on GitHub) One HTTP call, no clone GitHub returns "up to 300 changed files for the entire comparison" (https://docs.github.com/en/rest/commits/commits#compare-two-commits), so the largest diffs are the ones it truncates; a compare implementation per provider (GitHub, GitLab, Forgejo/Gitea, Bitbucket, Azure DevOps in pkg/scm); API quota
    (d) CI writes a diff summary into the Bundle No I/O at all Asserted by whoever creates the Bundle; an agent would report its own risk

    Choice: (b). It is the only option that scores a large change correctly and does not trust the author. The Job image is the render image with a risk mode (kardinal-render risk), so no new image is shipped.

    What it cannot do, and what would break it:

    • It cannot read a repository it has no credentials for. Then the ChangeRisk fails with SourceUnavailable and the tier is onFailure (default red, 4.4): fail closed.
    • For an image Bundle, head is spec.provenance.commitSHA, which CI asserts. An agent that creates a Bundle could name a small commit. When the Bundle's ImageVerification verified SLSA provenance (spec 20, #1963), the reconciler uses the verified source commit (ImageVerification.status.attestations[].slsa.sourceCommit, api/v1alpha1/imageverification_types.go:525-533; attestations.<name>.slsa.sourceCommit in gate CEL) and records sourceVerified: true. Otherwise a person's or a bot's version gets the sourceUnverified points (4.6), and an agent's is not scored at all (SourceUnverified, the onFailure tier, §14.1): the score is only as true as head, and the author must not name it.
    • go-git v5.19.2 (go.mod) has no partial-clone filter (no Filter in its CloneOptions), so the Job fetches head and base with depth 1 each. Fetching a commit by SHA depends on the server allowing it (GitHub, GitLab and Forgejo do for reachable commits). The implementation verifies this per provider in the SCM contract tests and falls back to a branch fetch deepened in steps up to the Job's limit. (RebaseOnRemote deepens once, to rebaseBaseDepth 200 commits, pkg/scm/git_rebase.go:64-68,139-151, then fails; the Job keeps deepening until limits.)
    • The termination message is at most 4096 bytes (pkg/renderjob/renderjob.go:43-44). Totals and class counts are exact; the path list is cut to fit and says so (pathsTruncated).

    4.3 RiskProfile: who sets the weights¶

    The weights decide what is green. Whoever can lower them can make their own changes green, so they must not live where an agent or a team under the policy can edit them alone.

    Mechanism For Against
    (a) Pipeline.spec.risk holds the weights and classes One object Whoever edits the Pipeline sets their own risk
    (b) A cluster-scoped profile Only admins write it One profile for every team; a team cannot add its own paths
    (c) A namespaced RiskProfile, in the Pipeline's namespace or an org policy namespace (--policy-namespaces), referenced by the Pipeline; the reference is a CEL variable, so org gates can require the org's profile Teams write their own, orgs pin theirs; the same trust split org gates already use (metricsNamespace, pkg/reconciler/policygate/reconciler.go:777-804) Two places to look; an org that cares must write the pin

    Choice: (c).

    apiVersion: kardinal.io/v1alpha1
kind: RiskProfile
metadata:
  name: default
  namespace: platform-policies
spec:
  classes:                         # at most 32; matched against every changed path in the Job
    - name: migrations
      globs: ["db/migrations/**", "**/*.sql"]
      points: 30
    - name: infra
      globs: ["**/*.tf", "charts/**/values-prod.yaml"]
      points: 25
    - name: security
      globs: ["**/rbac/**", "**/networkpolicy*.yaml"]
      points: 40
    - name: docs
      globs: ["docs/**", "**/*.md"]
      points: 0
    - name: frozen                 # RADAR-style scope exclusion: always red
      globs: ["billing/ledger/**"]
      forceTier: red
  weights:                         # every field optional; defaults in 4.6
    sizeBands: [{lines: 25, points: 5}, {lines: 75, points: 10}, {lines: 175, points: 15}, {lines: 375, points: 20}, {lines: 775, points: 25}]
    fileBands: [{files: 3, points: 2}, {files: 10, points: 5}, {files: 30, points: 8}, {files: 100, points: 10}]
    classesMax: 40
    actor: {human: 0, bot: 5, agent: 10, controller: 0, unknown: 10}
    sourceUnverified: 5            # a person's or a bot's version only; see requireVerifiedSource
    binaryFileLines: 100           # each changed binary file counts as this many lines in size
    baseMissing: 15
    historyPerFailure: 10
    historyMax: 20
  history:
    deployments: 30                # the window, matching deploymentMetrics (metricsLookbackBundles)
    directoryDepth: 2              # "apps/payments/x.go" → key "dir:apps/payments"
  tiers: {amber: 30, red: 60}      # score < 30 green, < 60 amber, else red
  onFailure: red                   # tier when the change cannot be scored: red | amber | green
  requireVerifiedSource: [agent]   # actor kinds whose version is scored only from verified provenance (§14.1)
  rollback: exempt                 # exempt | score
  limits: {timeout: 5m, maxRepoBytes: 2Gi}
status:
  ready: true
  conditions: [...]                # Ready; reasons Valid, InvalidGlob, InvalidBands
  observedGeneration: 4

    A RiskProfile reconciler validates what the schema cannot (each glob with the path.glob rules, §5.2; bands increasing) and writes status.ready. A ChangeRisk refuses a profile that is not ready for its current generation (ProfileNotReady, then onFailure).

    Pipeline.spec.risk holds only the reference and the source:

    spec:
  risk:
    profileRef: {namespace: platform-policies, name: default}   # own namespace or an org policy namespace
    source:                       # the application repository, for image Bundles
      repoURL: https://github.com/example/checkout
      secretRef: {name: checkout-src}   # labelled kardinal.io/referenceable=true, read by name

    • Run once.     • Rollback.     4.5 The Job¶

    Inputs: the ChangeRisk spec, status.base, the profile's classes and limits, as environment and a mounted Secret (as pkg/renderjob takes them). It has no Kubernetes credentials (automountServiceAccountToken: false), a NetworkPolicy of its own that allows DNS and the git host only, created by the reconciler and owned by the ChangeRisk as AgentRun creates one per run (pkg/reconciler/agentrun/reconciler.go:568-610; the render Jobs' chart NetworkPolicy, render.networkPolicy.enabled, is off by default and is not relied on), the in-process network lock RenderRun's Jobs use (renderjob.LockNetwork, pkg/renderjob/network.go:93: only git to the one host), runAsNonRoot, read-only root filesystem, an emptyDir work volume bounded by maxRepoBytes, and activeDeadlineSeconds from timeout.

    Work: fetch base and head (4.2), diff the two trees (rename detection on), count added and deleted lines of text files, count binary files (text or binary is decided from the content, as git does, by a NUL byte in the first 8000 bytes; .gitattributes in the repository is ignored, since the author writes it), match every changed path (both sides of a rename) against every class with the pkg/pathglob matcher that also backs path.glob (5.2), derive the directory keys, and write the result as JSON to the termination message, trimming paths from the end until it fits. It never reads commit messages.

    Output: diff in 4.4. The reconciler computes the score; the Job only measures. Reading the history and the actor needs the API server, which the Job must not reach.

    4.7 Rollback history of paths¶

    The history factor needs past outcomes per key. The ChangeRisk of an old Bundle is gone: kro deletes it with its Graph when the Bundle is retired (ledger G15), and Bundles beyond historyLimit (default 50, api/v1alpha1/pipeline_types.go:81-87) are deleted. So:

    • The Bundle reconciler copies the scored result into Bundle.status.risk (score, tier, keys, profile), once, when the ChangeRisk turns terminal. It is its own status; it reads ChangeRisk.
    • The ChangeRisk reconciler takes the Pipeline's last history.deployments (30) deployments, as the Pipeline's change failure rate defines them, from the Bundles still present, and counts the failed ones whose status.risk.keys intersect this change's keys.

    The deployment and failure definitions are one function: spec 28's pkg/delivery.Derive(pipeline, bundles, steps) []Entry (28-actor-analytics.md §5.5), onto which computeStability (pkg/reconciler/pipeline/metrics.go:316-498) is refactored; it is used by the Pipeline metrics, the DeploymentLog, the history factor and so the agent records (7). If this spec's risk score (rows 1-8 of §18) lands before spec 28, it lands that refactor first, under spec 28's names. The window is the same 30 deployments the change failure rate uses (metricsLookbackBundles, pkg/reconciler/pipeline/metrics.go:44). With historyLimit below 30 the window is what is left; factors[history].value says how many deployments were read.

    Keys are classes and directory prefixes, not files: a file-level history would need every path of every past change, which neither the termination message nor a status can hold, and DRS's folder feature is the same idea at a coarser grain.

    5. path.glob()¶

    5.1 Is there an equivalent?¶

    Checked:

    • cel-go v0.31.0 ext/: bindings, comprehensions, encoders, formatting, guards, lists, math, native, network, protos, regex, sets, strings. No glob or path function (grep -ri glob finds only isGlobalUnicast and "global functions" in ext/network.go, and GlobalEnum in tests).
    • k8s.io/apiserver v0.37.1 pkg/cel/library: authz, cidr, format, ip, jsonpatch, lists, quantity, regex, semver, urls. No glob.
    • kro v0.10.0-rc.0 pkg/cel/library: hash, json, lists, maps, omit, random, runtime. No glob. The Graph environment (pkg/cel/environment.go:128-156) adds cel-go ext and the Kubernetes libraries above; kro's docs list the same (website/versioned_docs/version-0.10.0-rc.0/docs/concepts/expressions/02-cel-libraries.md).
    • kardinal's PolicyGate environment (pkg/reconciler/policygate/cel_evaluator.go:107-165): ext.Strings, json, maps, lists, random, changewindow.*. No glob.

    The closest equivalent is standard CEL matches() (RE2). It has the same power, and a glob can be translated to a regex. It is not a substitute in practice: the glob semantics users already write in kardinal (Subscription pathGlob, matched with doublestar, pkg/source/git_remote.go:470-497, and RiskProfile classes) must agree with the gate's; * must stop at /, **/ must match zero or more directories, and dots and brackets must be escaped. A hand-written regex for charts/**/values-prod.yaml is ^charts/(?:[^/]+/)*values-prod\.yaml$, which policy reviewers do not read reliably. So a function is added (design rule 2: no equivalent in cel-go ext or the kro library).

    5.2 Semantics¶

    path.glob(pattern string, path string) -> bool
    • A global function in the path namespace, like json.marshal and hash.sha256.
    • Matches the whole path against pattern, /-separated:
    • * matches any run of characters except /; ? one character except /;
    • [abc], [a-z], [!a], [^a] a character class (no /);
    • ** as a whole segment (a/**/b, **/x, a/**) matches zero or more segments; elsewhere ** acts as * (doublestar's rule);
    • \ escapes the next character.
    • No {a,b} alternatives. doublestar expands them by recursion (doublestar/v4/match.go:224-250, the case '{' of doMatchWithSeparator), which is exponential in nested alternatives. Use || in CEL or two globs in a class. A pattern with an unescaped { is invalid.
    • Case-sensitive. Paths are not cleaned: a/./b does not match a/b, and a leading / is significant. Paths from risk.paths are always repository-relative without a leading /.
    • Errors (the call is an evaluation error, so a gate fails closed): an invalid pattern, a pattern longer than 256 bytes, a path longer than 4096 bytes, a non-string argument.
    • When pattern is a literal, it is validated at compile time by a cel.ASTValidators entry (cel-go cel/validator.go:93-116, the same mechanism as ValidateRegexLiterals), so policygate.ValidateExpression, the UI's validate endpoint and kardinal policy simulate reject a bad pattern before a gate is written.

    The matcher is pkg/pathglob: doublestar v4's Match (already a dependency, go.mod:18) behind a pattern check that refuses { and the length limits. The RiskProfile reconciler and the Job use the same package, so a class and a gate agree on every path.

    5.3 Cost¶

    Without alternatives doublestar keeps one backtrack point for * and one for ** (doMatchWithSeparator, match.go:95), so one call is O(len(pattern) × len(path)) in the worst case. The library declares this to the cost checker (checker.OverloadCostEstimate / interpreter.OverloadCostTracker, as cel-go's network library does in ext/network.go:309,337):

    • estimate: ceil(maxLen(pattern) × maxLen(path) / 64) + 1, with unknown sizes taken as the limits (256 × 4096 / 64 = 16,385);
    • actual: ceil(len(pattern) × len(path) / 64) + 1.

    risk.paths.exists(p, path.glob("db/**", p)) over 64 paths of 100 bytes costs about 64 × 3 = 192, far below the PolicyGate limit of 1,000,000 per evaluation (celCostLimit, cel_evaluator.go:47).

    5.4 Registration¶

    • PolicyGate environment. pkg/cel/library/path.go, a cel.Lib with LibraryName() path and a version option, shaped like kro's hash.go (pkg/cel/library/hash.go:79-100 in kro), added to newEvaluator (cel_evaluator.go:107). Documented in docs/reference/cel-context.md and docs/policy-gates.md.
    • kro. Proposed as the same library in kro's pkg/cel/library and coreDeclarations (pkg/cel/environment.go:128-156), with its cost functions. kro declares no cost functions for its libraries today (none in pkg/cel/library), and the Graph controller runs without a cost limit by default (--cel-cost-limit 0, cmd/controller/main.go:149-152), so the proposal must bound the function itself (the length limits), not rely on the limit. doublestar is already in kro's module graph (go.mod:42, indirect). Ledger G23 has the entry; nothing is posted.
    • kardinal does not need path.glob in Graph CEL for this spec: gates evaluate in the PolicyGate reconciler. It is proposed because a Graph user has the same need (an includeWhen over a path field), and so that one implementation serves both environments once gate CEL moves onto the Graph (ledger G8, "PolicyGate CEL").

    7. Earned autonomy¶

    7.1 Definitions¶

    The record is spec 28's: every figure is computed from the DeploymentLog entries of spec 28 (28-actor-analytics.md §5.4), with its definitions (§5.1) and its pure functions in pkg/delivery (Derive, Merge, Summarize, §5.5), onto which computeStability is refactored. This spec defines none of its own, so the agent's record and the Pipeline's deploymentMetrics cannot disagree.

    • Deployment: a Bundle whose change reached a final environment (a final-environment step started its health check with a change to apply), once per Bundle: one DeploymentLog entry. Not deployments: no-op promotions, steps a supersession cancelled, rollback Bundles (pipeline_types.go:1485-1494).
    • Failed deployment: an entry with failed: true: a final-environment step ended Failed, AbortedByAlarm or RollingBack after its health check started, a rollback Bundle later rolled it back (rollbackFrom), or it was rejected after it was deployed (pipeline_types.go:1496-1503).
    Field Definition
    deployments the agent's entries (bucket agent:<name>, 28 §5.2) with deployedAt in the window, across every DeploymentLog
    failedDeployments of those, failed
    changeFailureRate failedDeployments / deployments (DORA change fail rate)
    rollbacks the agent's entries that a rollback entry names in rollbackFrom (a subset of failed)
    reworkDeployments Summarize's rework for the bucket: rollbacks the agent shipped, and fixes (fixOf, 28 §5.4) of a production failure (DORA deployment rework)
    reworkRate Summarize's rework rate: rework deployments over all deployments by the agent, rollbacks included in both (28 §5.1)

    Rework is DORA's: the share of an agent's own deployments that were firefighting. A fixer agent has a high rework rate by design, so policies should use it for agents that are not fixers, and changeFailureRate and rollbacks for every agent. fixOf is asserted by the author (28 AA3), so rework is the one figure an agent can raise or lower by what it claims; policies should not reward a low rework rate.

    Not in this spec: a pre-production failure rate. A DeploymentLog records only versions that reached a final environment, so an agent whose versions a Pipeline keeps out of its final environments (environments[].agents: deny, pipeline_types.go:200-208) has no record, and agent.trackRecordSufficient stays false for it (which, in the policies of 7.5, asks for a person). A rate over pre-production steps needs DeploymentLog to record pre-production outcomes too, a follow-up of spec 28; reading live PromotionSteps instead would be a second, non-durable source.

    Window. Time-based: the last spec.trackRecord.windowDays days (default 30, 7 to 90) by deployedAt, and trackRecordSufficient requires at least spec.trackRecord.minDeployments (default 10) deployments in it. A DeploymentLog keeps entries up to maxAge (90 days by default, 28 §5.4), so every allowed window is covered unless maxEntries dropped entries (below). The Pipeline metrics use the last 30 deployments per Pipeline instead; that window cannot be summed across Pipelines, so the agent window is by time, as spec 28's (28 §5.7). RADAR's per-source lookback is 60 days with a minimum count; 30 is DORA's usual period.

    The exact mechanism, read path to gate:

    1. pkg/reconciler/deploymentlog (spec 28) writes DeploymentLog.status.entries from the Pipeline's Bundles and steps, in the Pipeline's namespace, only its own status. This spec adds one field to an entry, riskTier (green, amber, red, or empty), copied from Bundle.status.risk.tier (4.7) when the Bundle has one; the log reconciler already reads the Bundle. It is fixed once the entry is final, as the rest of the entry.
    2. A new track-record reconciler (per AgentIdentity) lists the DeploymentLogs that hold its agent through a field index on status.actors[].key (agent:<name>, 28 §5.4) from the manager's cache, calls pkg/delivery.Summarize over the agent's entries in its window, and writes AgentIdentity.status.trackRecord: its own status, read from another kind's status, no cross-kind write. A DeploymentLog watch whose predicate fires only when status.actors or an agent's entries changed maps the event to the agents in the old and new logs. It requeues itself at the time the oldest counted entry leaves the window; reading the clock there is allowed, since it writes the result to its own status (computedAt).
    3. The PolicyGate reconciler builds agent.* (7.3) from AgentIdentity.status.trackRecord read from the cache, as it builds the rest of agent.* today (actor_context.go:69-99). No gate lists DeploymentLogs or computes a rate: the gate path reads one status field, which a reconciler wrote before the gate ran (spec 28 §10 requires exactly this).

    Neither a Graph node nor a Graph ref is involved: agent.* is the PolicyGate reconciler's context, as today (schedule.* and metrics.* are too), and the track record is reconciler-written status, the Graph-first form for data that must outlive every Bundle (a Graph is per Bundle and is deleted with it, ledger G15).

    • Truncation. A DeploymentLog drops entries beyond maxEntries (100 by default) and sets its Truncated condition (28 §5.4); a deleted log is recreated and seeded from the live objects with the condition Reseeded (28 §12). The agent's trackRecord.truncated is true when a counted log is Truncated and its oldest kept entry is newer than the window start, or is Reseeded with the condition's lastTransitionTime inside the window: in both, entries of the window may be gone. Policies can require !agent.trackRecordTruncated.
    • Not the IndexReconciler. Today's AgentIdentity status writer is agentidentity.IndexReconciler, which handles one fixed request and runs one actor.Evaluate over every AgentIdentity, writing the AgentIndex and every AgentIdentity's status (pkg/reconciler/agentidentity/reconciler.go:97-100, 157,388-401), and watches AgentIdentities with no predicate. Its watch gains a predicate that ignores status.trackRecord changes, so a track-record write does not rebuild the index, and the two reconcilers write disjoint status fields (trackRecord; ready, reason, conditions) with merge patches.
    • Sharding. AgentIdentity is cluster-scoped. The track-record reconciler registers through shard.Active().Complete, so its cluster-scoped requests run only on the shard that OwnsClusterScoped (pkg/shard/shard.go:242,286-291); the DeploymentLog reconciler is sharded by namespace (28 §5.5). The manager's cache is cluster-wide unless --watch-namespace is set (cmd/kardinal-controller/manager_options.go:165-177); the shard gate filters reconciles, not the cache, so the owning shard reads every DeploymentLog. With --watch-namespace the record is that namespace's only; the docs say so.
    • Merge order. Spec 28's DeploymentLog (its §5.4-5.6, pkg/delivery, the reconciler and the historyLimit guard) lands before this spec's earned autonomy (§18 rows 9 and 10). The risk score (§4-6) does not depend on it.
    • Ledger. Spec 28's G8 row says of the log "Display data: no promotion decision reads it". With earned autonomy a decision reads it, through AgentIdentity.status.trackRecord; whichever PR lands second updates that row (§19).

    What it cannot do, and what would break it:

    • No pre-production failure rate (CR19). The log holds final-environment deployments only (28 §2, "Deployment"), so an agent's failures in test or uat are not in its record, and an agent kept out of every final environment (environments[].agents: deny) has no record at all; its trackRecordSufficient stays false, which in the policies of 7.5 asks for a person. A pre-production rate needs spec 28 to log pre-production outcomes (§18 row 16); reading live PromotionSteps in the meantime would be a second, non-durable source with its own definition.
    • Not live. The record is as fresh as two reconcilers: the log's, on a final-environment step's transition, then the track record's, on the log's change. A gate evaluated between a failure and the track-record write sees the previous record (computedAt says when it was made). Stopping an agent at once after a failure is spec 17's suspension, not this.
    • One cluster. An agent's deployments through another cluster's controller are not counted; with --watch-namespace, only that namespace's (Sharding, above).
    • A deleted log loses its history. Spec 28 reseeds it from the live objects, so failures older than the retained Bundles are gone. Spec 28's admission covers CREATE and UPDATE only (28 §11), so <release>-risk-owners also refuses an agent's DELETE of a DeploymentLog (§11), and a reseed inside the window sets trackRecord.truncated (above), so a person's deletion is visible to policies.
    • Asserted rework. fixOf is the author's claim (28 AA3): the rework rate is the one figure an agent moves by what it says (7.1).
    • It starts short. At upgrade the log holds what spec 28 seeds from the retained Bundles (§15).
    • What would break it: a gate that lists DeploymentLogs or computes a rate (the gate path must read one status field); an entry's riskTier changing after the entry is final; the track-record reconciler writing anything but AgentIdentity.status.trackRecord, or the IndexReconciler reconciling on that write (a loop between the two).

    The budgets item of v0.14 (spec 24) does not count from these records: it keeps its own ledger in AgentIdentity.status.usage (24-agent-budgets.md §5.2). The two can be reconciled later if the definitions converge.

    8. Risk-adaptive soak and approvals¶

    8.1 Soak¶

    The variables exist: upstream.<env>.soakMinutes (minutes since this Bundle was Verified there, pkg/reconciler/policygate/reconciler.go:894-908) and bundle.upstreamSoakMinutes (the minimum over the gated environment's direct upstreams, reconciler.go:635-647,744-775; computed only when the expression names it, not for requiredWhen). With risk.*:

    expression: 'upstream.uat.soakMinutes >= (risk.tier == "red" ? 720 : risk.tier == "amber" ? 180 : 60)'
message: "uat soak scales with change risk"

    Nothing else is needed. The gate re-evaluates on its recheckInterval (default 5m, reconciler.go:73) and on every ScheduleClock tick, as soak gates do today (the PolicyGate controller has no Bundle watch; docs/policy-gates.md lists what wakes a gate). The Bake of an environment (pipeline_types.go:257-262, 496-529) is a different thing, a contiguous healthy window inside the step; it stays static per environment, and §9 makes it per wave.

    8.2 Approvals by tier¶

    8.3 DRS gating levels¶

    The DRS weekend, yellow and red levels are combinations of variables kardinal already has:

    # Weekend: block the riskiest 5% (DRS "weekend"); everything else as usual.

---
# A declared high-traffic period: a ChangeWindow "peak" blocks amber and red.

    peak is a blackout ChangeWindow over the high-traffic period.     8.4 A docs-only fast path¶

    expression: 'risk.scored && !risk.pathsTruncated && risk.paths.all(p, path.glob("docs/**", p) || path.glob("**/*.md", p))'

    It is used as requiredWhen: "!(<that>)" on an approval, so a docs-only change needs none. !risk.pathsTruncated is required: all() over a truncated list could pass for a change that also touched code.

    9. Fleet wave presets¶

    9.1 Today¶

    A fleet environment expands into one environment per target, in target order (pkg/graph/fleet.go:85-142); maxConcurrent admits at most N targets in flight, ranked by order (pkg/graph/compact.go:347-366); maxUnavailable stops new starts after N failures (compact.go:359-366); an environment after the fleet waits for every target (fleet.go:170-210). That is a sliding window, not waves: with maxConcurrent: 3 the fourth target starts as soon as any of the first three is Verified. There is no "this group must be done and baked before the next starts", and the bake is one value for every target (EnvironmentSpec.Bake, copied to each target, fleet.go:127-139). Fleets are only built in the compact shape (compact.go:80-113).

    Preset Waves (size, bake) Default maxUnavailable

    aws takes the upper end of "two to four hours" and the article's 12 hours after the first wave. aws-fast is for pre-production fleets and is not from the article. The values are frozen: changing them is a breaking change with a new preset name.

    Rules:

    • size is a count (1 or more) or a percentage of the targets ("10%", rounded up, at least 1), as maxUnavailable (fleet.go:145-168). The last wave may omit it; only the last.
    • A fleet smaller than the waves fills them in order and drops the empty ones: 4 targets with aws give (1), (1), (2).
    • bakeMinutes replaces the environment's bake.minutes for that wave's targets. The bake policy, maxDuration and health come from the environment (and a target's health override) as today. 0 means no bake.
    • maxConcurrent still caps the targets in flight, inside a wave too.
    • Validation in the schema: at most 10 waves; sizes positive; only the last without a size; waves and wavePreset not both set.
    • Targets of a selector fleet (Application, ClusterProfile) are ordered by name, as status.fleets resolves them (pkg/reconciler/pipeline/fleets.go:46-48); that order is the wave order. To put the low-traffic target first, use static targets (their list order) or a new kardinal.io/fleet-order label on the selected objects, which fleetTargets (fleet.go:45-79) would sort by, then by name, when present.

    9.4 Mechanism¶

    • Builder (pkg/graph/fleet.go): fleetMembers assigns each target its wave and sets the target's spec.Bake.Minutes from the wave (fleet.go:127-139, where the target's spec is built), so the PromotionStep reconciler, which reads the target's spec through EnvironmentSpecFor (fleet.go:225-240, findEnv at pkg/reconciler/promotionstep/reconciler.go:3008-3015), bakes it without a change. expandFleets (fleet.go:176-210) gives each target of wave k > 1 the targets of wave k − 1 as upstreams, in place of the fleet's upstreams. Every consumer of the DAG (SoakUpstreams, pkg/graph/upstreams.go:44-56, over DirectUpstreams, for bundle.upstreamSoakMinutes; kardinal explain; the UI) then sees the waves.
    • Compact admission (compact.go:326-366): already waits for upstreamGroups, one per fleet, done when every member is Verified or Superseded and at least one is Verified (compact.go:333-343, upstreamGroups at compact.go:617). Grouping changes from "per fleet" to "per fleet and wave", so a wave-2 target's group is the wave-1 targets. maxConcurrent, maxUnavailable and paused apply unchanged. The DAG entries gain wave (shown, not read by CEL).
    • Status: no new list. Pipeline.status.environments already has one entry per fleet target (a fleet environment expands to its targets, pkg/reconciler/pipeline/environments.go:32-39), with its state and since; each entry gains fleetWave (the target's wave; 0 outside a fleet with waves), which the UI and kardinal get pipelines group by (prod wave 2/5 1/1 Verified). A separate list of each wave's target names would repeat every target name in the Pipeline status, the controller's most-written object (#1719), and Pipeline.status.fleets[] cannot hold it either: that list holds only resolved selector fleets (Application and ClusterProfile), not static fleets or Target selectors (pkg/reconciler/pipeline/fleets.go:46-62, pipeline_types.go:1281-1287). fleetWave is display only, as the rest of environments (no controller decision reads it, pipeline_types.go:1289-1293); the builder assigns waves from the spec and the targets.

    What would break this: a failed target keeps its wave from completing, so the next wave never starts, which is the intent (AWS stops on an alarm). A target removed from a selector fleet while its wave is in flight is kept by keepRemovedFleetTargets (pkg/reconciler/bundle/reconciler.go:1048-1056). A membership change rebuilds an in-flight Bundle's Graph in place (pipeline_types.go:736-741; FLEET-04), so the wave assignment of its remaining targets shifts too; steps already started keep their spec.

    9.5 Risk-adaptive waves¶

    A gate on the fleet environment applies to every target (pipeline_types.go:242-249), and with wave edges bundle.upstreamSoakMinutes of a wave-k target is the soak of wave k − 1, so the bake between waves can scale with risk without any Graph change:

    expression: 'bundle.upstreamSoakMinutes >= (risk.tier == "red" ? 720 : risk.tier == "amber" ? 240 : 60)'

    For the first wave the upstream is the environment before the fleet, so the same gate also asks that environment to soak. Choosing a different wave list per tier in the Graph would need the step spec to read the ChangeRisk; a PromotionStep template node with a pending field is wholly Unresolved (ledger G14), so all steps would wait on the score (option (c) of 4.8). Not done.

    13. Scale¶

    • Per Bundle: one ChangeRisk object (about 3 KB status), one Job run (seconds to minutes; a depth-1 fetch of two commits). A Pipeline that creates 200 Bundles a day starts 200 Jobs. The ChangeRisk reconciler limits concurrent Jobs with a slots.Limiter of its own (pkg/slots, shipped in #2123; MetricCheck and ChangeRequest each have one, cmd/kardinal-controller/main.go:423-437), flags --change-risk-max-jobs (default 8) and --change-risk-max-jobs-per-namespace (default 2). Supersession lowers the load: the reconciler does not create the Job of a Bundle that is Superseded or Rejected before it starts (phase Failed, reason Superseded, no tier needed: no gate of that Bundle will run).
    • Graph: one node per Bundle; it adds one object to G9's per-walk cost and counts toward MaxGraphObjects (4,500, pkg/graph/size.go:28), with about 200 bytes of spec and a 260-byte inventory estimate toward MaxGraphBytes (1,200,000, size.go:22,35; G10).
    • Gates: risk is read from the cache, only for gates that mention it.
    • History factor: reads the Pipeline's retained Bundles from the cache (ListPipelineBundles, indexed), once per ChangeRisk.
    • Agents: the track-record reconciler, a new per-agent reconciler (not the IndexReconciler, which evaluates every AgentIdentity in one pass and must not read logs), reads only the DeploymentLogs its field index names. For an agent active in 1,000 Pipelines that is 1,000 cached logs (spec 28 §13 budgets about 25 KB each) and up to 100,000 entries per reconcile; reconciles of one agent are coalesced by the work queue. A log holds at most maxEntries (100) entries, so the cost does not grow with time.
    • Fleets: waves add no node; the admission expression is the existing one with a different grouping. Wave edges add at most (size of wave k − 1) upstreams per target of wave k: for the aws preset on 500 targets, wave 5 (483 targets) each lists 12 upstreams, about 6,000 entries in the DAG def, inside the existing G10 check (pkg/graph/size.go). Explicit waves can be larger (a wave of 100 followed by 400 targets would write 40,000 entries), so the DAG data stores each wave's member list once and each entry names its upstream wave by index, keeping the size O(targets). The implementation measures it in the scale suite.
    • Multi-tenant: profiles, ChangeRisks, Jobs and Secrets stay in the Pipeline's namespace; an org profile is read-only to teams.

    14. What this does not protect against¶

    • A wrong head commit. Without verified provenance, the score is of the commit CI named (4.2).
    • Changes outside the diff. A risky value in a Secret, a cluster setting, a dependency bumped in the base image: none are in the commit range.
    • Calibration. Defaults are judgement (4.6). A green tier means "the profile gives few points", not "safe".
    • Gaming by splitting. An agent can split a large change into small versions. Supersession and budgets (v0.14) limit the rate; the track record by tier (7.5) keeps small greens from earning red autonomy.
    • Padding the record. Trivial real deployments count toward deployments. Use the per-tier counts.
    • Path names chosen by the author. A file named docs/x.md that a build includes as code is matched as docs. Classes describe paths, not what the build does with them.

    14.1 Can an agent lower its own risk score?¶

    Every input of the score, who controls it, and what keeps the author of a version (an agent, or the person or CI job behind it) from lowering it. "Author" is whoever created the Bundle.

    Input Who sets it Can the author lower it? What stops it
    actor factor the Bundle's actor stamp No Admission checks the stamp against the AgentIndex (<release>-actor, spec 17): an agent cannot stamp itself human or bot
    head (image Bundle) spec.provenance.commitSHA, written by the author Yes, without verified provenance: it names a small commit, and the Job scores that requireVerifiedSource (default [agent]): an agent's version is scored only from the source commit of verified SLSA provenance (spec 20); without it the ChangeRisk fails SourceUnverified and takes the onFailure tier (red).     The track record (§7) is the other score an agent would want lower. It counts only Bundles that reached a final environment, from the controller's own deployment and failure definitions; an agent can pad it with small deployments (the residual "Padding the record"), which the per-tier counts expose (7.5). It cannot delete its failures: the records live in DeploymentLog.status, which only the controller writes (28 §11), and <release>-risk-owners refuses an agent's DELETE of a DeploymentLog (§11), whose reseed would forget failures older than the retained Bundles (7.2).
